# repo_map (#49) — требования с флагами сложности (шаг requirements-complexity)

## Таблица требований

| # | Требование | Флаг | Почему |
|---|---|---|---|
| 1 | MCP-тул `repo_map(repo, level, focus)` в engineering-skills | 🟡 | Новый тул в общем каталоге tools/: проходит check-mcp-conformance (#1481 «никогда пусто») и provider-manifest в CI |
| 2 | Ответ < 1 с из кеша; L0 ≤ 2k токенов (подсчёт токенайзером) | 🟡 | Производительность/бюджет — определяет агрегацию модулей, а не срез сырого индекса (~300k) |
| 3 | Кеш по commit sha (инвалидация по sha + хешу модуля); хранение вне worktree в `<mirrorsRoot>/repo-maps/<repoId>/<sha>/` | 🟡 | Меняет существующий контракт пути индекса v1 (`.engineering/index` внутри копии) — потребителей (prepare_task, repo_context) перевести; старые индексы игнорируются, данных не теряем |
| 4 | Сборка карты при `engineering_spawn_workspace` — в фоне, спавн не замедляется | 🟡 | Внедрение в hot-path спавна через общие hooks (`workspace.js` afterWorktree/afterSpawn) |
| 5 | Сборка карты нового sha main после мержа (v1: лениво при первом обращении / в точке ensureMirror) | 🟡 | Точка внедрения общий жизненный цикл; конкретный триггер фиксируется на шаге архитектуры. Не ⚫: поведение «карта отсутствует → строим / failed → сырой репо» уже определено в сценарии |
| 6 | L0-описания одной строкой: дешёвая LLM (OpenRouter, свой fetch без ядра), кеш по хешу модуля; без ключа/недоступна → структура без описаний | 🟡 | Внешняя интеграция (сеть/ключ); поведение деградации определено, L1 от LLM не зависит |
| 7 | L1 детерминированный: парсер JS/TS, fallback regex-скан индекса, без LLM | 🟢 | Локально в новом модуле |
| 8 | Fallback на сырой репо при любой проблеме карты; тул не возвращает пустой ответ; чужой sha/репо/схема игнорируется | 🟢 | Усиливает существующий контракт индекса, ничего не отменяет |
| 9 | Правило «сначала repo_map L0 → L1 focus → чтение» в плейбуках feature/debugging (`explore-context`/`bug-context`) и `prompt-domains/engineering.md` | 🟢 | Аддитивный текст инструкции, пересборка `npm run build:playbooks` |
| 10 | Языки старта JS/TS/Python/MD; прочие — строкой пути с пометкой в L1 | 🟢 | Ограничение объявлено, не-цель в сценарии |
| 11 | Lock по sha для параллельных сборок (spawn + мерж); retention N последних sha | 🟢 | Локальное состояние нового кеша, один сценарий |
| 12 | PR-ветка: карта main + дельта изменённых файлов ветки в шапке | 🟢 | Локальная логика нового тула, поведение в шапке определено |
| 13 | Кеш живёт под workspaceRoot/mirrorsRoot профиля, не в общем /tmp | 🟢 | Реальное ограничение окружения (слоты ta-agent-N) |
| 14 | Приёмка: юнит-снапшоты фикстуры, инвалидация, A/B на 10 задачах, замер <1 с / ≤2k | ⚪ | Проверка, не поведение системы |

## 🔴 / ⚫

Нет.
- 🔴 (права/безопасность/биллинг/необратимые миграции/мульти-тенантность): ничего — тул читает уже доступный агенту репозиторий, кеш обратим (удаление папки), LLM вызывается только внутри сессии владельца с его же ключом.
- ⚫ (противоречия/неопределённые состояния): спорные места сценария уже закрыты допущениями; все развилки поведения (нет карты, нет LLM, чужой sha, пустой репо) имеют определённый исход с фолбэком на сырое чтение.

Челлендж не требуется. Ближайшая развилка — парсер JS/TS: вендор `acorn` (JS + regex для TS) против `typescript` + `npm ci` в deploy.sh ядра (второй репозиторий). Флаг 🟡, обратимая, рекомендация шага контекста: acorn-вендор; выносится на шаг архитектуры одной строкой с рекомендацией, без меню владельцу.
