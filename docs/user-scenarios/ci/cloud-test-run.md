# Прогон тестов в облаке: ci-setup (разовый) и ci-run (частый)

Статус: planned (план 3e40a139, 2026-09-29).
Область: CI/CD. Репозитории-носители: `trained-assist/software-engineering-playbooks`
(плейбуки + MCP-тул), целевые репозитории — любые (первый: trained-assist/trained-assist-agent).

## Ценность

**Агент/разработчик получил полный результат прогона тестов ветки (зелёный/красный + упавшие
тесты и хвост лога) из облака, не занимая локальную машину минутами и не зная GitHub Actions.**

Акторы:
- **Владелец репозитория** (настраивает один раз) — репозиторий получил ручной запуск полного
  набора тестов для любой ветки (`workflow_dispatch`), дальше всё делается одной командой.
- **Агент в сессии** (пользуется часто) — перед открытием PR вызвал `ci-run` и получил ответ,
  вместо 3–13 минут локального прогона и ручного опроса CI.

## Доказанность: **V5**

Источник: логи сессий 25–29.09.2026 — 492 локальных прогона тестов в 82 сессиях (~3,5 ч),
31 прогон дольше 2 мин (до 13 мин, таймауты), ~2,3 ч опроса CI; `gh workflow run` почти не
используется, потому что у репозиториев нет `workflow_dispatch`. Это задокументированный
обходной путь, которым уже пользуются; решение владельца от 29.09.2026 — «сетап 1 раз, потом
легко; и для других юзеров, не только для нас».

## Сценарий 1 — ci-setup (разовый, на репозиторий)

Актор: агент по просьбе владельца репозитория.

1. **КОГДА** владелец просит «настрой прогон тестов в облаке для <repo>» (или `ci-run` на этом
   репозитории ответил «не настроено») **ТОГДА** агент запускает
   `playbook_run(playbook_id: "ci-setup", goal: <ссылка на репозиторий>)`.
2. **КОГДА** плейбук анализирует целевой репозиторий **ТОГДА** он определяет стек
   (node/python/…) по manifest-файлам и перечисляет существующие `.github/workflows/*`.
3. **КОГДА** в репозитории уже есть workflow с `workflow_dispatch`, запускающий полный набор
   тестов **ТОГДА** плейбук завершается с ответом «уже настроено» и не открывает PR
   (идемпотентность повторного запуска).
4. **КОГДА** `workflow_dispatch` отсутствует или покрывает не весь набор **ТОГДА** плейбук
   создаёт/дополняет workflow: входной параметр `ref` (ветка/коммит), опциональный выбор
   набора (unit / scenario / staging), `concurrency` по `ref` (новый запуск отменяет старый
   той же ветки), без шагов мержа и деплоя; при отсутствии CI вообще — из шаблона
   `templates/ci.yml` (примеры для типовых стеков).
5. **КОГДА** изменения готовы **ТОГДА** плейбук открывает PR в целевой репозиторий
   (ветка `eng/…`, база `origin/main`) и доводит его до зелёного CI и мержа штатным
   пайплайном.
6. **КОГДА** PR смержен **ТОГДА** владелец получает объяснение простыми словами: что появилось
   (ручной запуск тестов на любой ветке), как запустить (одна команда / кнопка в Actions),
   что запуск ничего не мержит и не деплоит.

## Сценарий 2 — ci-run (частый, на ветку)

Актор: агент в сессии (в т.ч. шаг плейбуков feature/debugging «Полная локальная проверка»).

1. **КОГДА** нужен полный прогон тестов ветки **ТОГДА** агент вызывает MCP-тул
   `ci_run_branch(repo, ref, suite?)` (`src/mcp-skills/tools/63-ci-cd.js`) — либо плейбук
   `ci-run` сам вызывает этот тул.
2. **КОГДА** в репозитории нет настроенного ручного запуска **ТОГДА** тул отвечает
   «не настроено» и предлагает запустить `ci-setup` (по команде — запускает его).
3. **КОГДА** настройка есть **ТОГДА** тул делает `workflow dispatch` на `ref`, находит свой
   запуск (свежайший run этого workflow на этот ref с event `workflow_dispatch`) и возвращает
   его идентификатор.
4. **КОГДА** запуск ещё выполняется **ТОГДА** ожидание идёт durable-wait'ом с короткими
   опросами (≤2 мин за ход, не блокирует процесс), а не одним длинным зависанием.
5. **КОГДА** запуск завершён успешно **ТОГДА** ответ: «зелёный», набор, ветка, длительность.
6. **КОГДА** запуск упал **ТОГДА** ответ: «красный», список упавших джоб/тестов + хвост лога
   (последние строки упавшей джобы) — достаточно, чтобы агент починил код, не открывая GitHub.
7. **КОГДА** запуск отменён/пропущен GitHub (внешняя ошибка) **ТОГДА** тул возвращает
   явную ошибку с причиной, а не «зелёный».
8. **КОГДА** шаг плейбуков feature/debugging «Полная локальная проверка» идёт перед открытием PR
   **ТОГДА** локально гоняются только быстрые unit/lint, ветка пушится, а полный набор идёт
   в облаке тем же `ci_run_branch`; репозиторий не настроен → полный прогон остаётся локальным,
   и агент предлагает `ci-setup`.

## Не-цели

- Не автоматизируем мерж PR и деплой этим же workflow — прогон только читает и проверяет.
- Не заменяем PR-пайплайн (ci + staging-gate на PR остаются как есть).
- Не переписываем существующие workflow репозиториев сверх необходимого (только добавляем
  `workflow_dispatch`/параметры).
- Не поддерживаем «красный ≠ блокер по желанию» — общий skip/continue-on-error запрещён
  (правило владельца 2026-09-16).
- Нет отдельного UI — только команда/тул и ответ в чате.

## Крайние случаи

- **Репозиторий без CI вообще** → ci-setup создаёт workflow из шаблона с нуля.
- **Повторный ci-setup** → идемпотентно: «уже настроено», без PR.
- **Параллельные запуски одной ветки** → `concurrency` по ref: новый отменяет старый.
- **Долгий прогон (>15 мин)** → durable-ожидание с опросами, шаг не умирает по таймауту хода.
- **Нет прав на запись в репозиторий** → ci-setup отвечает, что нужен доступ, ничего не ломает.
- **Намеренно сломанный тест** → ci-run обязан показать красный результат и упавший тест.
- **Чужой юзер без знания GitHub Actions** → всё через плейбук; человеку объясняют простыми
  словами, что появилось.
