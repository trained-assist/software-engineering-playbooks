# Сценарий: плейбук `skill-tool` — новый MCP-инструмент в доменном скиле

Источник: issue #53 (из бэклога #50, п.6), одобрено владельцем 29.09.2026. Соседние сценарии в
`docs/user-scenarios/` отсутствуют — это первый; процессные соседи — плейбуки `feature`,
`debugging`, `new-software` (`playbooks-src/`).

## Ценность

**Актор:** владелец продукта (через агента-исполнителя, который ведёт план).
**Результат:** новый MCP-инструмент доменного скила вызывается в живой сессии агента и
возвращает ожидаемый ответ — одним запуском плейбука, без ручной сборки цепочки
«файл → схема → тест → регистрация → PR → релиз → проверка».

Негативная ценность (то, чего НЕ должно случиться): «тул смержен, но в сессии его нет»
и «описание в промпт-домене расходится со схемой тула» — плейбук не даёт закрыть план в этих
состояниях.

**Доказанность: V3** — прямой запрос реального пользователя (владельца) в issue #53/#50,
подкреплённый разбором ~13 000 команд его сессий за 10 дней (задача названа «повторяется
постоянно»). До V5 не хватает счётчика: сколько раз за период реально добавлялся тул вручную.
Для процессной фичи уровня «шаблон в библиотеке» этого достаточно.

## Шаги (КОГДА → ТОГДА)

| # | Актор/блок | КОГДА | ТОГДА система |
|---|---|---|---|
| 1 | MCP `playbook_run(playbook_id: "skill-tool", goal, vars: {repo})` | владелец/агент запускает плейбук с целью «тул X в скиле Y» | создаётся durable-план из шагов `skill-tool@<version>`; без `repo` и без GitHub-ссылки в цели → `INPUT_REQUIRED` |
| 2 | Шаг «скил-репо и конвенции» (`engineering_spawn_workspace`, `engineering_repo_context`) | исполнитель стартует первый шаг | выдан workspace на ветке `eng/<profile>-plan-<id>`; в итоге шага: путь каталога тулов (`src/mcp-skills/tools/NN-*.js`), следующий свободный номер, способ регистрации (авто-обнаружение реестра / явный список), соседний тул-образец |
| 3 | Шаг «заготовка» | конвенции известны | в ветке закоммичен файл тула: имя с префиксом домена, JSON-схема входа, описание для модели (что делает, когда звать, пример), хендлер; пустой/ошибочный вход → осмысленный ответ, не исключение |
| 4 | Шаг «исполняемый тест» (`npm test` репо скила) | заготовка есть | есть unit-тест хендлера + тест регистрации (тул находится через реестр, имя/схема совпадают); тесты зелёные локально — гейт |
| 5 | Шаг «правило в промпт-домене» | тул меняет поведение агента (новый сценарий, порядок вызовов) | правило добавлено в промпт-домен скила и ссылается на реальное имя тула и его параметры; не меняет → шаг закрыт `⏭ не нужно — почему` |
| 6 | Шаг «PR» (`github_create_pr`, CI `ci` + `staging-gate`) | ветка готова | открыт PR; ждём (durable wait) зелёные CI и staging на актуальной версии → автосквош-мерж; красное → autofix/новый PR, не пуш в тот же PR |
| 7 | Шаг «релиз» (`ssh vm "curl -s localhost:8080/health"`, `readlink -f /home/vova/agent-master`, чекаут скила рядом с релизом) | PR смержен | подтверждено: прод-релиз/чекаут скила содержит мерж-коммит; зелёный deploy-джоб не считается доказательством |
| 8 | Шаг «тул виден в новой сессии» | релиз подтверждён | в НОВОЙ сессии агента тул есть в списке инструментов (MCP перезапущен) — гейт |
| 9 | Шаг «реальный вызов» | тул виден | вызов из живой сессии с реальными (не тестовыми) аргументами вернул ожидаемое; результат/ответ приложен к итогу — гейт; тестового мусора в проде не остаётся |

## Не-цели
- Не генерируем тул целиком «по описанию» — плейбук задаёт шаги и гейты, логику пишет исполнитель.
- Не покрываем изменения ядра (core MCP в trained-assist-agent) и шлюза tg-bot — для этого `feature`
  и будущий плейбук «изменение через два репо» (#50 п.5).
- Не делаем экспозицию тула в `provider-manifest.json`/UI каталога скилов, если скил этого не требует.
- Не меняем рантайм плейбуков (durable waits, валидаторы) — только новый источник в `playbooks-src/`.

## Крайние случаи
- Нет `repo` → `INPUT_REQUIRED` на старте (как у остальных инженерных плейбуков).
- Имя тула уже занято (в этом или другом скиле) → шаг 3 падает с конфликтом, а не перезаписывает.
- В скиле нет тестового раннера → шаг 4 добавляет минимальный `node --test`, а не пропускается.
- Тулу нужны креды внешнего сервиса → шаг 9 ждёт кредов (durable wait, awaiting_user), не фейкует вызов.
- Внешний сервис лежит на шаге 9 → повтор по таймеру; не «успех» по моку.
- Смержено, но MCP не перезапущен/не в релизе → шаг 8 не проходит, план не закрывается.
- Повторный запуск плейбука на тот же тул → тот же workspace по `root_task_id`, без дублей файлов.

## Приёмка плейбука
0. Петля сценария: `npm run test:sandbox:skill-tool` — 9 шагов сценария через реальные блоки репо
   (builder, схема/тесты, собранный плейбук), уровень S3, цикл ≤10 с. До реализации красная
   («источника ещё нет»); гейты сценария живут только здесь.
1. `playbooks/skill-tool.json` собран `npm run build:playbooks` и проходит `tests/playbooks.test.js`
   (схема `contracts/playbook.schema.json`, свежесть сборки).
2. Один пробный прогон на реальном маленьком туле до успешного вызова в живой сессии.

## Открытые вопросы (помечены как риск, не блокируют)
- Кандидат для пробного прогона: issue предлагает «инструмент из п.2 бэклога» («что с PR»), но он
  не маленький (сжатие логов, несколько API). Рекомендация: маленький read-only тул в одном скиле;
  выбор — на шаге пробного прогона.
- Проверка «тул виден в новой сессии» пока ручная/полуавтоматическая (через новую сессию агента);
  автоматизация — вне этого плейбука.
