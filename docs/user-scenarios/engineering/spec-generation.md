# Сценарий: генерация ТЗ (спецификации) в инженерном репозитории

Эпик: https://github.com/trained-assist/software-engineering-playbooks/issues/43 (Директивы 2.В / 3, голос 28.09.2026).
Закрывает пункты requirements-log «Перенос генерации ТЗ из freelance-skill в engineering» (R1–R17).

## Актор и ценность

Актор: агент-исполнитель в сессии владельца trained-assist (любая аудитория, включая freelance), а также
владелец/рекрутер, который просит «собери ТЗ по проекту».

Ценность: контекст проекта превращается в техническое задание о СИСТЕМЕ (long + short) с инженерной
конкретикой и проверяемым блоком «как запускается и как проверяется». Генерация живёт в этом
репозитории (модуль `src/mcp-skills/tools/65-spec-generation.js`, правила — `src/spec-generation/rules.js`,
промпт-домен — `src/prompt-domains/spec-generation.md`), рядом с движком сложности, который используется
вторично. Прежние `freelance_generate_*` удалены из freelance-скила.

## Текущее состояние (после переноса, 2026-10)

- Тулы: `engineering_generate_spec` (контекст → `spec/_source.md` + `long.md` + `short.md`, short — не сжатие
  long), `engineering_get_spec` (точечная правка готового ТЗ), `engineering_generate_all` (батч по каталогу),
  `engineering_generation_note` (постоянная инструкция генерации), `engineering_spec_generation_defaults` /
  `engineering_spec_generation_explained` (настройки/справка).
- Содержание обязательно для ОБОИХ вариантов: какая инфраструктура поднимается, какой тестовый сервер/порт,
  кто с кем общается и по какому протоколу/очереди, по шагам «что именно делается». Long несёт полный раздел
  «Как запускается и как проверяется» (команды, фикстуры, наблюдаемый сигнал, уровень S0–S5, что в петле
  делает человек); short — пункт «Как проверяем» на 1–3 строки.
- Стиль — отдельный переключаемый параметр: по умолчанию `oldschool` (анти-AI ЧБ-олдскульный), прежний вид
  доступен как `style: 'modern'`; неизвестный стиль — ошибка, не тихий фолбэк. Правила стиля зафиксированы
  в коде (`src/spec-generation/rules.js`), не в переписке.
- Маршрутизация: для аудитории `freelance` резолвер агента подставляет engineering-модуль
  (`65-spec-generation.js`) и промпт-домены `spec-generation` + `engineering`; в freelance-скиле не осталось
  ссылок на удалённые тулы (проверено на живом релизе).
- Смоук-образцы стиля: `docs/examples/spec-long-classic.md`, `docs/examples/spec-short-classic.md`.
- Тесты контракта: `tests/spec-generation-rules.test.js` (канонические строки правил),
  `tests/spec-generation-tool.test.js`; песочница `scripts/sandbox/spec-generation.mjs`.

## Шаги (КОГДА → ТОГДА)

1. Генерация. КОГДА пользователь просит «собери/сделай ТЗ по проекту X», ТОГДА агент вызывает
   `engineering_generate_spec(context_dir)`: сначала нормализация контекста в `spec/_source.md`, затем
   независимо пишутся `long.md` и `short.md` по правилам из `src/spec-generation/rules.js`.
2. Точечная правка. КОГДА нужно изменить готовое ТЗ, ТОГДА `engineering_get_spec(context_dir)` → правка по тому
   же пути, без перегенерации с нуля; `spec/tz.md` читается как long (legacy read-compat).
3. Постоянная инструкция. КОГДА владелец хочет изменить поведение генерации для всех следующих запусков,
   ТОГДА `engineering_generation_note(text, context_dir?, mode)` — профиль
   `~/agent-data/spec-generation/_generation.md` или проектный `<context_dir>/spec/generation.md`
   (проектный приоритетнее).
4. Батч. КОГДА нужно обработать много контекстов сразу, ТОГДА `engineering_generate_all(root, since)` —
   сначала сводная таблица, затем генерация по каждому контексту.
5. Проверка. КОГДА нужна проверка контракта, ТОГДА `node --test tests/spec-generation-*.test.js` и песочница
   `npm run sandbox:spec-generation`; e2e — `npm run test:e2e` (или явная фиксация скипа по отсутствию
   окружения).

## Границы (что НЕ делаем)

- Третий вариант документа не заводим, если он содержательно дублирует long/short.
- Этап 2 («спецификация глубже в инженерную тему»: инженер генерирует ТЗ для себя при планировании,
  ideation «5 направлений → выбрать оптимальный») — отдельная задача, не в этом сценарии.
- Сейлз-форма («любой документ → более сейлзовый вид») — отдельная операция, в генератор не встраивается.
- Движок сложности (`src/complexity/`) не дублируется: оценка используется вторично в разделе
  «Стоимость и сроки», если уже есть в контексте.
