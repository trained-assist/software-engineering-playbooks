# Сценарий: быстрый discovery через сжатую карту репозитория (repo_map L0/L1)

Эпик: https://github.com/trained-assist/software-engineering-playbooks/issues/49 (бэклог #50 п.1, одобрено владельцем 2026-09-29).
Закрывает пункт requirements-log «[планируется] Сжатый индекс репозитория для мини-ресерча в define-use-case».

## Актор и ценность

Актор: агент-исполнитель инженерного плейбука (feature / debugging) в сессии владельца trained-assist.

Ценность: агент за один вызов (< 1 с из кеша) получает сжатую карту репозитория и находит нужные файлы
без листания исходников — локализация не хуже, discovery-вызовов (`sed -n`/`grep`) минимум на 50 % меньше,
значит дешевле и быстрее каждая инженерная задача.

Негативная ценность (тоже должна держаться): агент НЕ получает устаревшую карту чужого sha/репо как актуальную
и НЕ теряет корректность — при любой проблеме карты он прозрачно падает на чтение сырого репо.

## Доказанность ценности: V5

Источник: разбор ~13 000 команд терминала из сессий владельца за 10 дней (issue #50) — ~480 вызовов
`sed -n`/`grep -n`/`grep -rn` для поиска «где что лежит». Это обходной путь, которым пользуются сейчас и за
который платят токенами/временем. Плюс явная просьба владельца 29.09 и давний пункт requirements-log.

## Что уже есть (переиспользуем, не пишем заново)

- `src/index/*` + `scripts/index-repo.js` — детерминированный индекс v1 (`docs/INDEXER.md`): files/modules/symbols
  (regex)/tests, `revision.json` с sha и repo id, stale/foreign-индекс игнорируется, fallback на raw-repo.
- `prepare_task(prefer_index)`, `engineering_repo_context` — потребители индекса.
- Структурное сжатие диффов в pr-autofix (v1.5.0) — образец «честной шапки» об опущенном.
repo_map — надстройка над индексом: L1 рендерится из symbols (+ парсер языка, ранжирование по графу ссылок),
L0 — из modules + однострочные LLM-описания с кешем.

## Шаги (КОГДА → ТОГДА)

1. Спавн workspace. КОГДА агент вызывает MCP `engineering_spawn_workspace(repository_url, root_task_id)` и для
   base sha нет карты, ТОГДА система в фоне строит индекс + L0/L1 для этого sha и возвращает workspace, не
   дожидаясь карты (спавн не замедляется); статус карты виден в `engineering_workspace_status`.
2. Мерж в main. КОГДА PR смержен в main репозитория, ТОГДА фоном строится карта нового sha main; L0-описания
   пересчитываются только для модулей, чей хеш содержимого изменился (остальные из кеша).
3. Карта L0. КОГДА агент на шаге define-use-case / локализации вызывает MCP `repo_map(repo, level: 0)`,
   ТОГДА за < 1 с (кеш) возвращается текст ≤ 2k токенов: модули/папки → назначение одной строкой, точки входа,
   где конфиг/тесты/деплой, «куда смотреть, если…», и шапка: sha, что опущено, как получить L1/полный файл.
4. Скелет L1 с фокусом. КОГДА агент вызывает `repo_map(repo, level: 1, focus: ["<символ или путь>", …])`,
   ТОГДА возвращается скелет (5–15k токенов): сигнатуры экспортов/функций/классов + первая строка doc-комментария,
   файлы ранжированы по важности, файлы, связанные с focus, — наверху; в шапке — сколько файлов/символов опущено.
5. Точечное чтение. КОГДА агент выбрал 1–5 файлов по L0/L1, ТОГДА он читает только их (L2 = обычное чтение) и
   делает правку; `sed/grep` для поиска «где лежит» не нужны.
6. Плейбук. КОГДА запускается плейбук feature или debugging, ТОГДА инструкция шага define-use-case /
   локализации явно говорит «сначала repo_map L0 → L1 focus → чтение файлов», и то же правило есть в
   `src/prompt-domains/engineering.md`.
7. PR-ветка. КОГДА агент работает на ветке с изменениями относительно main, ТОГДА repo_map отдаёт карту main
   + дельту изменённых файлов ветки (помечено в шапке), а не устаревшую картину.

## Крайние случаи

- Карты для sha ещё нет (строится / упала): `repo_map` строит синхронно, если укладывается в лимит, иначе
  отвечает явным статусом `building`/`failed` с советом читать сырое репо — не молчит и не отдаёт чужой sha.
- Карта другого репо/схемы/sha → игнорируется (как в индексе v1).
- LLM (OpenRouter) недоступна или без ключа → L0 собирается без описаний (только структура), в шапке
  «описания недоступны»; L1 от LLM не зависит вообще.
- Неподдерживаемый язык (не JS/TS/Python/MD) → файл попадает в L1 только строкой пути/размера, помечен.
- Пустой / огромный репо: L0 всё равно ≤ 2k токенов (обрезка с честной пометкой «опущено N модулей»).
- Повторный вызов на том же sha → ответ из кеша, без LLM-вызовов (детерминированно, байт-в-байт для L1).
- Приватный репо без доступа → та же ошибка доступа, что у spawn_workspace, без частичной карты.
- Параллельные сборки одного sha (spawn + мерж) → одна сборка, второй ждёт/берёт результат (lock по sha).

## Не-цели

- Эмбеддинги / векторный поиск.
- GitHub MCP (решение владельца 29.09).
- LLM в L1 (L1 строго детерминированный).
- Замена чтения файлов: L2 остаётся обычным чтением, сырое репо — fallback навсегда.
- Языки кроме JS/TS/Python/MD на старте.

## Приёмка (исполняемая)

- Юнит: снапшот L0/L1 на фикстуре-репо стабилен; инвалидация по sha и по хешу модуля работает.
- Прод: `repo_map` на trained-assist-agent отвечает < 1 с из кеша, L0 ≤ 2k токенов (подсчёт токенайзером).
- A/B-бенч на 10 закрытых задачах (issue → файлы смерженного PR): доля верно локализованных файлов по L0+L1
  не хуже контроля; число discovery-вызовов до первой правки — минус ≥ 50 %.

## Открытые вопросы / риски (закрыты допущениями, без вопроса владельцу)

- Где лежит кеш: допущение — рядом с mirror репозитория в engineering-workspaces (per host, per repo, per sha),
  не в дереве worktree. Риск: две VM строят каждая свой кеш — приемлемо.
- Триггер «после мержа в main»: допущение — хук в существующем пост-мерж/деплой-потоке (или lazy-сборка при
  первом `repo_map` на новом sha main). Уточнить на шаге архитектуры.
- tree-sitter — нативная зависимость; если не ставится в окружении, fallback на regex-скан индекса v1.
