# Плейбук `new-software` — Новый софт или модуль с нуля (Playbook Zero)

> Сгенерировано `scripts/build-playbooks.js` из `playbooks-src/new-software.json` и `library/step-types.json`. Правь источники, не этот файл.

**Когда:** Делаем что-то без привязки к текущему продукту и максимально свободны в архитектуре: новый сервис, модуль, инструмент, прототип. Здесь решение об инфраструктуре и песочнице определяет скорость всего проекта.

**Результат:** Ключевой сценарий новой системы работает в реальном окружении; у проекта есть песочница, CI и живые доки, остальные сценарии заведены как следующие фичи.

- Цель этого плейбука — не вся система, а ходячий скелет: ОДИН ключевой сценарий end-to-end в реальном окружении + песочница + CI. Остальные сценарии становятся issues и идут через плейбук feature.
- Циклы — норма: если разведка или песочница показали, что выбранный подход невозможен, вернись к вариантам (опиши в итоге шага и предложи пользователю), а не тащи неработающее решение.

**Запуск:** `playbook_run(playbook_id: "new-software", goal: "<что делаем>", vars: {repo: "<owner/repo>"})` → черновик плана → `task_update(status: "active")`.

## Шаги подробно

### Стадия «Рамка: сценарии, инфраструктура, аналоги, сложность»

#### 1. Сценарий пользователя: ценность и шаги

```text
Тип шага: define-use-case — Зафиксировать, КАКУЮ ценность получает пользователь и через КАКИЕ шаги — это вход для тестов, песочницы и проверки результата.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Мини-ресерч ДО вопросов: найди в репозитории существующий сценарий на эту тему (docs/user-scenarios/, docs/requirements-log.md, соседние сценарии). Если он есть — дополняй его, а не пиши новый; если желание пользователя понятно из соседних историй — не мучай его анкетой, а скажи «нашёл сценарий X, понял так-то».
2. Ценность — как РЕЗУЛЬТАТ для конкретного актора, одной фразой. Может быть негативной. Примеры: «API-клиент получил ответ о цене товара»; «пользователь бесплатного тарифа не смог вызвать платную фичу»; «атакующий не получил кредов».
3. Оцени доказанность ценности по лестнице V (ниже) и запиши уровень с источником.
4. Шаги — хронологические шаги взаимодействия актора с системой до успеха, с указанием КОНКРЕТНЫХ функциональных блоков: экран/кнопка UI, эндпоинт API, команда CLI, MCP-тул, сообщение бота. Для каждого шага — ожидаемый результат в форме «КОГДА <событие> ТОГДА система <ответ>» (EARS / Given-When-Then).
5. Не-цели (что сознательно НЕ делаем) и крайние случаи (пустые данные, ошибка внешнего сервиса, повтор, права).
6. Если есть пробелы — ОДНО сообщение пользователю: ≤5 вопросов, у каждого твой рекомендуемый ответ («правильно ли я понял: …?»), плюс что улучшит фичу («если добавить X — будет сильно лучше»). Отправь и уйди в ожидание: task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопросы>) → DURABLE: waiting. Когда ответ придёт — шаг перезапустится с ним.
7. Запиши/обнови сценарий в docs/user-scenarios/<область>/<slug>.md целевого репозитория (или в итоге шага, если репозиторий ещё не выбран).

Лестница доказанности ценности (V) — насколько мы уверены, что это кому-то нужно:
  • V5 — есть явная ссылка, где ценность получают сейчас (платят / уже пользуются обходным путём)
  • V4 — много пользователей просят, есть документ custdev или поисковый спрос
  • V3 — есть отзывы / фича-реквесты от реальных пользователей
  • V2 — экспертная оценка сейлза/маркетолога, говорящего с клиентами (норм для средней фичи)
  • V1 — экспертная оценка инженера (норм для мелкой фичи)
  • V0 — не указано (норм только для нестрогой работы)
  Правило: Уровень не блокирует работу. Но если для нетривиальной фичи V ≤ 1 — ЯВНО скажи пользователю: «ценность не подтверждена, риск сделать не то» и предложи, что добавить, чтобы стало лучше.

Готово, когда: Записаны Ценность (с уровнем V) и Шаги с конкретными функциональными блоками и ожидаемыми результатами; открытые вопросы либо закрыты, либо явно помечены как риск.

Для этого плейбука:
- Для новой системы: 1–3 ключевых сценария, первым — тот, без которого системы нет. Он и станет ходячим скелетом.

Общее для плейбука «new-software»:
- Цель этого плейбука — не вся система, а ходячий скелет: ОДИН ключевой сценарий end-to-end в реальном окружении + песочница + CI. Остальные сценарии становятся issues и идут через плейбук feature.
- Циклы — норма: если разведка или песочница показали, что выбранный подход невозможен, вернись к вариантам (опиши в итоге шага и предложи пользователю), а не тащи неработающее решение.
```

#### 2. Разведка инфраструктуры и уровней доступа

```text
Тип шага: infra-discovery — Понять пространство решений: на чём и с какими доступами можно построить песочницу — от этого зависит, насколько автономно агент сможет работать.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Инвентаризация того, что доступно агенту БЕЗ пользователя: машины (VM, локальные Mac'и), облака (GCP, Cloudflare), GPU, сеть/порты, тулчейны (node/python/xcode/docker), подключённые сервисы и ключи профиля (ls ~/agent-tokens/<profile>, env), CI. Проверяй командами, а не предположениями.
2. Что есть у пользователя, но не у агента: устройства (телефон, другие ноутбуки), аккаунты провайдеров, прод-доступы, железо.
3. Для каждого внешнего сервиса предложи УРОВНИ доступа (нет / только чтение / отдельный sandbox-проект / полный) и что каждый уровень даёт для песочницы.
4. Прототип следующего шага: набросай 1–2 кандидата песочницы, чтобы понять, какой доступ реально нужен («а вдруг у пользователя есть X — тогда можно S5»).
5. Одним сообщением спроси пользователя про уровни доступа (с рекомендацией для каждого) → task_item_wait(awaiting_user: true, …) → DURABLE: waiting. Креды, которые он пришлёт через ZeroCreds, можно ждать условием until: {credential_present: "<service>"}.
6. Итог: таблица «ресурс → доступ агента → что даёт → чего не хватает».

Лестница автономности песочницы (S) — может ли агент сам замкнуть цикл «изменил → увидел результат»:
  • S5 — полный замкнутый цикл: агент сам поднимает окружение и прогоняет сценарий end-to-end за минуты (локально / эфемерно, внешние зависимости — фейки или песочницы провайдеров)
  • S4 — стейджинг с реальными зависимостями, куда агент сам деплоит и где сам наблюдает результат
  • S3 — автотесты с моками внешних зависимостей (unit/integration), без полного e2e
  • S2 — код запускается частично; внешние эффекты (прод-креды, железо, платежи) проверяет человек
  • S1 — только статический анализ/компиляция; поведение проверяет человек
  • S0 — нет исполнения вообще (код пишется вслепую)
  Правило: Скорость агента ≈ 1 / время замкнутого цикла без человека. Всегда целься в максимально достижимый S и явно называй его и время цикла. S4–S5 = «проект выглядит несложно, пилим».

Готово, когда: Есть таблица ресурсов и доступов, согласованная с пользователем, и оценка максимально достижимого S.
```

```text
Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):

Для этого плейбука:
- Для нового софта исследование в основном ВНЕШНЕЕ: как это делают другие, open-source, SaaS, стандарты. Отдельно — что из наших репозиториев можно переиспользовать.
```

#### 4. Сложность требований: флаги и челлендж

```text
Тип шага: requirements-complexity — Не тащить в реализацию требования, которые умножают сложность системы, без явного решения.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Выпиши требования списком (из сценария + неявные: права, платформы, данные, интеграции, производительность).
2. Каждому поставь флаг ⚪🟢🟡🔴⚫ (шкала ниже) с одной фразой «почему».
3. Для каждого 🔴 и ⚫ — челлендж: сколько новых состояний/веток × сценариев придётся тестировать, какие типичные баги, во сколько раз растёт система, какая дешёвая альтернатива даёт ту же ценность (например, вместо новой модели ролей — один флаг на профиле).
4. Проверь источник каждого требования: задача или реальное ограничение другой части системы. «Так уже написано» — не источник: такой код меняем, а не подстраиваемся.
5. Если есть 🔴/⚫ — одно сообщение пользователю с таблицей и рекомендацией → task_item_wait(awaiting_user: true, …) → DURABLE: waiting. Без 🔴/⚫ — сообщи коротко и иди дальше.
6. Итог: минимальный набор требований с флагами и принятые решения по 🔴/⚫.

Флаги сложности требований — чем выше флаг, тем больше требование плодит состояний, веток и тестов по всей системе:
  • ⚪ прозрачный — не меняет поведение/модель (текст, цвет, копирайт)
  • 🟢 зелёный — аддитивно и локально, один сценарий, без новых контрактов
  • 🟡 жёлтый — задевает общие контракты/схему данных/интеграцию/вторую платформу/производительность
  • 🔴 красный — модель доступа и прав, границы безопасности/аутентификации, биллинг, необратимая миграция данных, мульти-тенантность
  • ⚫ чёрный — неоднозначность: пересекающиеся сценарии с разным поведением, противоречия, неопределённые состояния
  Правило: 🔴 и ⚫ челленджим ВСЕГДА — и для себя, и для пользователя: во что обойдётся (сколько новых состояний × сценариев тестировать, какие баги типичны), какая дешёвая альтернатива даёт ту же ценность. Требование существует, только если идёт из задачи или из реального ограничения ДРУГОЙ части системы — «так уже написано» не источник требований. ⚫ разрешается до дизайна.

Готово, когда: Все требования помечены флагами; 🔴/⚫ либо сняты, либо явно подтверждены пользователем с пониманием цены; ⚫ разрешены.
```

### Стадия «Выбор подхода»

#### 5. Варианты решения, ранжированные по песочнице

```text
Тип шага: solution-options — Сгенерировать подходы, максимально повторяющие функциональность в песочнице, и выбрать оптимальный.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. 2–4 принципиально разных подхода (включая «купить/взять готовое» и «самый простой, который работает»).
2. Для каждого: достижимый уровень S и время цикла, стоимость (деньги/сложность), риски, обратимость, соответствие реальным ограничениям из разведки.
3. Ранжируй: при прочих равных выигрывает подход с более высоким S — он даёт агенту скорость на всём проекте.
4. Зафиксируй решение как ADR (контекст → решение → последствия → отвергнутые варианты) в docs/adr/ или в итоге шага.
5. Если выбор неочевиден или зависит от денег/доступов пользователя — спроси одним сообщением с рекомендацией и жди (awaiting_user).

Лестница автономности песочницы (S) — может ли агент сам замкнуть цикл «изменил → увидел результат»:
  • S5 — полный замкнутый цикл: агент сам поднимает окружение и прогоняет сценарий end-to-end за минуты (локально / эфемерно, внешние зависимости — фейки или песочницы провайдеров)
  • S4 — стейджинг с реальными зависимостями, куда агент сам деплоит и где сам наблюдает результат
  • S3 — автотесты с моками внешних зависимостей (unit/integration), без полного e2e
  • S2 — код запускается частично; внешние эффекты (прод-креды, железо, платежи) проверяет человек
  • S1 — только статический анализ/компиляция; поведение проверяет человек
  • S0 — нет исполнения вообще (код пишется вслепую)
  Правило: Скорость агента ≈ 1 / время замкнутого цикла без человека. Всегда целься в максимально достижимый S и явно называй его и время цикла. S4–S5 = «проект выглядит несложно, пилим».

Готово, когда: Есть ранжированная таблица вариантов и записанное решение (ADR) с обоснованием через S.
```

### Стадия «Песочница и каркас»

#### 7. Песочница: замкнутый цикл, который повторяет сценарий

```text
Тип шага: sandbox — Сделать так, чтобы агент сам, без человека, одной командой прогонял сценарий и видел результат — это главный ускоритель всей разработки (sandbox-driven development).

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Выбери целевой уровень S (максимально достижимый при текущих доступах) и назови время цикла, которого хочешь добиться.
2. Построй цикл: тест/скрипт/харнесс, который проходит Шаги сценария через реальные функциональные блоки (API/CLI/UI-автоматизация), с фейками или sandbox-аккаунтами внешних зависимостей, фикстурами и сидом данных.
3. Одна команда запуска (например scripts/sandbox/<slug>.sh или конкретный npm test -- <file>), детерминированный вывод pass/fail.
4. Докажи цикл: запусти его СЕЙЧАС — он должен падать по правильной причине (фичи ещё нет / баг воспроизводится). Зелёный до изменений = песочница ничего не проверяет.
5. Если уровень S упирается в доступ — не жди внутри рана: попроси доступ у пользователя и task_item_wait(until: {credential_present: "<service>"} или awaiting_user) → DURABLE: waiting.
6. Закоммить песочницу (она часть результата) и опиши запуск в итоге шага.

Лестница автономности песочницы (S) — может ли агент сам замкнуть цикл «изменил → увидел результат»:
  • S5 — полный замкнутый цикл: агент сам поднимает окружение и прогоняет сценарий end-to-end за минуты (локально / эфемерно, внешние зависимости — фейки или песочницы провайдеров)
  • S4 — стейджинг с реальными зависимостями, куда агент сам деплоит и где сам наблюдает результат
  • S3 — автотесты с моками внешних зависимостей (unit/integration), без полного e2e
  • S2 — код запускается частично; внешние эффекты (прод-креды, железо, платежи) проверяет человек
  • S1 — только статический анализ/компиляция; поведение проверяет человек
  • S0 — нет исполнения вообще (код пишется вслепую)
  Правило: Скорость агента ≈ 1 / время замкнутого цикла без человека. Всегда целься в максимально достижимый S и явно называй его и время цикла. S4–S5 = «проект выглядит несложно, пилим».

Готово, когда: Одна команда прогоняет сценарий и сейчас падает по правильной причине; уровень S и время цикла записаны.

Для этого плейбука:
- Для нового софта песочница — это окружение целиком (локально/эфемерно, фейки внешних сервисов) + сценарий-харнесс ключевого сценария. Это первый код проекта.
```

### Стадия «В реальное окружение»

#### 12. CI зелёный (ждём; чиним, если красный)

```text
Тип шага: ci-green — Довести PR до зелёного CI, не сидя в ране: ждём дёшево, просыпаемся, когда CI закончил.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Посмотри статус чеков PR (gh pr checks <url>).
2. Ещё идут → task_item_wait(until: {ci_green: "<PR url>"}, poll_every_sec: 300, timeout_sec: 7200, reason: "ждём CI") → DURABLE: waiting. Сервер разбудит, когда CI закончится (зелёный — условие выполнено; красный — «окончательно не выполнилось»).
3. Красный → разберись по логам (gh run view --log-failed), почини. PR неизменяемы: фикс — новой веткой от этой и НОВЫМ PR (старый закрой со ссылкой «superseded by»); если в репо работает pr-autofix и он уже открыл фикс-PR — используй его. Напечатай новую строку «PR: <url>» и снова жди CI.
4. Зелёный → комментарий в issue, DURABLE: done.

Готово, когда: Все чеки PR зелёные (детерминированная проверка ci_green).
```

```text

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).
```
