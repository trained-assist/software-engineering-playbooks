# Плейбук `debugging` — Отладка: баг, регрессия, ошибка в логах

> Сгенерировано `scripts/build-playbooks.js` из `playbooks-src/debugging.json` и `library/step-types.json`. Правь источники, не этот файл.

**Когда:** Что-то работает не так, как должно: репорт пользователя, ошибка в логах, упавший сценарий, регрессия после релиза. Главная работа — поднять уровень воспроизведения R; фикс без воспроизведения — спекулятивный.

**Результат:** Ошибка устранена в корне и подтверждённо не возвращается в реальном окружении; есть регрессионный тест.

- Порядок неслучаен: без воспроизведения нет уверенного фикса, без регрессионного теста баг вернётся, без наблюдения в проде «починено» — гипотеза.

**Запуск:** `playbook_run(playbook_id: "debugging", goal: "<что делаем>", vars: {repo: "<owner/repo>"})` → черновик плана → `task_update(status: "active")`.

## Шаги подробно

### Стадия «Сбор контекста»

#### 1. Сбор контекста бага

```text
Тип шага: bug-context — Собрать все факты об ошибке до гипотез и поднять уровень R, насколько можно без воспроизведения.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Что говорит репорт: кто, когда, что делал, что ожидал, что получил. Точный текст ошибки.
2. Логи и история вокруг времени ошибки: journalctl / execution history / логи сервиса, частота (одиночная или регулярная), первое появление.
3. Что менялось незадолго: деплои, мержи (git log --since), конфиги, внешние сервисы.
4. Связанные issues / qa_log_lookup — не известная ли это проблема.
5. Оцени уровень R по лестнице ниже; если нужно больше данных от пользователя (шаги, скрин, время) — спроси одним сообщением и жди (awaiting_user).

Лестница воспроизведения (R) — насколько надёжно мы видим проблему:
  • R5 — воспроизведено автоматически в песочнице/стейджинге одной командой (тест или скрипт)
  • R4 — наблюдается в логах (сгенерировать ошибку сами не можем)
  • R3 — есть чёткие шаги воспроизведения от пользователя
  • R2 — есть конкретный (не дефолтный) текст ошибки / exception
  • R1 — есть факт ошибки, привязанный ко времени и модулю, без деталей
  • R0 — записано со слов
  Правило: Цель — поднять R максимально до фикса. Фикс при R < 3 помечается как «спекулятивный» и обязательно получает шаг подтверждения в проде (наблюдение за логами).

Готово, когда: Факты собраны, текущий уровень R записан с доказательствами.

Для этого плейбука:
- Локализация бага в коде — та же дисциплина, что и для фичи: `repo_map(level=0)` → `repo_map(level=1, focus=["<символ из стека или лога>"])` → чтение конкретных файлов, а не сплошной grep по репозиторию. Нет карты — читай сырой репо.

Общее для плейбука «debugging»:
- Порядок неслучаен: без воспроизведения нет уверенного фикса, без регрессионного теста баг вернётся, без наблюдения в проде «починено» — гипотеза.
```

### Стадия «Воспроизведение (песочница бага)»

#### 2. Воспроизведение: поднять R до песочницы

```text
Тип шага: reproduce — Превратить баг в автоматический красный тест/скрипт (R5) — дальше всё становится быстрым.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Попробуй R5: минимальный тест/скрипт, воспроизводящий ошибку одной командой в песочнице или на стейджинге. Минимизируй (убирай лишнее, пока ошибка остаётся).
2. Не получается сгенерировать — R4: настрой наблюдение. Ошибка регулярная → усни до её следующего появления: task_item_wait(until: {command_exit_zero: "journalctl -u <svc> --since '-10min' | grep -q '<сигнатура>'"}, poll_every_sec: 300, timeout_sec: <окно>, reason: "ждём повтора ошибки") → DURABLE: waiting. Когда она появится, шаг проснётся — снимай контекст (логи вокруг, входные данные) пока свежо.
3. Не хватает шагов от пользователя — R3: спроси точные шаги и жди (awaiting_user).
4. Запиши достигнутый R и почему выше нельзя. Фикс при R < 3 будет «спекулятивным».

Лестница воспроизведения (R) — насколько надёжно мы видим проблему:
  • R5 — воспроизведено автоматически в песочнице/стейджинге одной командой (тест или скрипт)
  • R4 — наблюдается в логах (сгенерировать ошибку сами не можем)
  • R3 — есть чёткие шаги воспроизведения от пользователя
  • R2 — есть конкретный (не дефолтный) текст ошибки / exception
  • R1 — есть факт ошибки, привязанный ко времени и модулю, без деталей
  • R0 — записано со слов
  Правило: Цель — поднять R максимально до фикса. Фикс при R < 3 помечается как «спекулятивный» и обязательно получает шаг подтверждения в проде (наблюдение за логами).

Готово, когда: Баг воспроизводится одной командой (R5), либо достигнут максимально возможный R с объяснением и настроенным наблюдением.
```

### Стадия «Причина и план фикса»

#### 3. Корневая причина

```text
Тип шага: root-cause — Найти источник, а не симптом, и понять, почему это не поймали раньше.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Гипотезы списком (научный метод): для каждой — какое наблюдение её подтвердит/опровергнет; проверяй на воспроизведении, а не рассуждением.
2. Если есть «раньше работало» — git bisect со скриптом воспроизведения.
3. 5 почему: от симптома к источнику (данные → код → контракт → процесс).
4. Почему не поймали: какого теста/проверки/алерта не хватило.
5. Тот же паттерн в других местах (rg по похожему коду) — список для фикса или отдельного issue.

Готово, когда: Корневая причина подтверждена воспроизведением; известно, какой проверки не хватало.
```

#### 4. План фикса: наименьшее изменение + регрессия

```text
Тип шага: propose-change — Спроектировать наименьшее изменение, закрывающее сценарий, и заранее определить, как проверим результат.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Proposal: зачем (сценарий + ценность), что меняется, влияние (модули, контракты, данные, другие сервисы).
2. Design: наименьшее изменение; затронутые файлы/модули; новые/изменённые контракты и данные; почему не проще.
3. Spec delta: какие сценарии ДОБАВЛЯЮТСЯ / МЕНЯЮТСЯ / УДАЛЯЮТСЯ в docs/user-scenarios (это потом «архивируется» в живые сценарии).
4. Срезы (tasks): маленькие проверяемые шаги реализации, каждый — со своим тестом; порядок.
5. План проверки: каждый Шаг сценария → автотест или сценарий песочницы; целевой уровень S.
6. Риски и откат: что может сломаться у других, как откатить (revert / флаг / миграция назад), нужна ли миграция данных.

Готово, когда: Есть proposal/design/срезы/план проверки/откат, достаточные, чтобы другой агент реализовал без вопросов.

Для этого плейбука:
- Для бага: фикс в источнике (не в симптоме); регрессионный тест = воспроизведение из шага «Воспроизведение»; тот же паттерн в других местах — чинить сразу, если дёшево, иначе отдельный issue.
- Оцени радиус поражения: кого ещё задела ошибка (данные, другие пользователи), нужна ли починка данных.
```

#### 5. Декларация плана: GitHub issue

```text
Тип шага: plan-declaration — Записать план туда, где его найдут, если этот ран/сессия умрёт: «учёный погиб в эксперименте — соратники нашли бумаги и довели до конца».

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Найди существующий issue на эту тему (gh issue list --search). Если есть — обнови, а не плоди дубль.
2. Создай/обнови issue в целевом репозитории: сценарий (ценность + шаги), итоги исследования, флаги требований и решения, proposal/срезы как чек-лист, план проверки, уровень S, ссылка на durable-план (Plan id).
3. Метки: task (+ bug для багов); приоритет комментарием.
4. Напечатай в итоге шага ссылку на issue — все следующие шаги будут дописывать туда прогресс комментариями.

Готово, когда: Issue существует, содержит план целиком, ссылка есть в итоге шага.

Для этого плейбука:
- Метка bug. В issue: уровень R, корневая причина, почему не поймали, план фикса.
```

### Стадия «Фикс»

#### 6. Реализация в изолированном workspace

```text
Тип шага: implement — Сделать изменение срезами, гоняя песочницу после каждого среза.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Workspace: engineering_spawn_workspace для репозитория, если доступен; иначе git worktree от свежего origin/main в отдельной папке. НИКОГДА не работай в общем checkout и в чужой ветке.
2. Ветка: <feat|fix|chore>/<slug>-<timestamp> — уникальная, твоя; сначала проверь, что такой нет (git ls-remote).
3. Срез за срезом из плана: сначала тест/проверка среза (красный), потом код (зелёный), потом прогон песочницы. Коммит на каждый срез (commit-first: не запускай незакоммиченный код).
4. Следуй конвенциям репозитория (README/CLAUDE.md), держи дифф минимальным, без попутных рефакторингов.
5. Если в процессе всплыло новое 🔴/⚫-требование — не решай молча: отметь в issue и спроси пользователя (awaiting_user).
6. Отметь прогресс по срезам комментарием в issue.

Готово, когда: Все срезы реализованы и закоммичены в своей ветке; песочница зелёная.

Для этого плейбука:
- Первый срез — регрессионный тест из воспроизведения: он красный до фикса и зелёный после. Без этого фикс не принимается.
```

#### 7. Полная локальная проверка

```text
Тип шага: verify-local — Дать полный ответ по тестам до пуша: локально — только быстрые проверки, полный набор — в облаке.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Локально — ТОЛЬКО то, что укладывается в секунды/минуты: syntax-check, lint, быстрые unit. Большой набор локально не гоняй: он и есть та проблема, ради которой этот шаг менялся.
2. Полный набор — в облаке: запусти ветку (git push -u origin <ветка>), затем ci_run_branch(repo: "{repo}", ref: <ветка>) и дождись дешёво: task_item_wait(until: {ci_run_green: {repo: "{repo}", run_id: <id>}}, poll_every_sec: 120, timeout_sec: 3600, reason: "ждём прогон тестов ветки") → DURABLE: waiting. Никакого busy-wait внутри рана.
3. Репозиторий не настроен (ответ configured:false) — так и напиши, прогони полный набор локально, как раньше, и предложи плейбук ci-setup (не запускай его молча).
4. Красное в облаке → почини новым коммитом в ту же ветку и повтори диспатч. Регрессии: прогони тесты модулей, которые задевает изменение.
5. В итоге — локальные команды и их результаты (exit codes, число тестов) плюс url рана в облаке и его итог.

Готово, когда: Полный набор тестов зелёный — в облаке, либо локально, если репозиторий ещё не настроен; результаты (локально и url рана) приведены.
```

```text
Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Перед пушем: ветка твоя (создана в этом плане), не main/master, нет открытого PR на эту ветку (PR неизменяемы — правки после открытия идут новой веткой и новым PR).

5. В итоге шага ОТДЕЛЬНОЙ строкой: PR: https://github.com/<owner>/<repo>/pull/<n> — по ней следующие шаги (CI, merge) найдут PR автоматически.

Готово, когда: PR открыт, ссылка напечатана строкой «PR: <url>».
```

### Стадия «Доставка и подтверждение»

#### 9. CI зелёный (ждём; чиним, если красный)

```text
Тип шага: ci-green — Довести PR до зелёного CI, не сидя в ране: ждём дёшево, просыпаемся, когда CI закончил.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Посмотри статус чеков PR (gh pr checks <url>).
2. Ещё идут → task_item_wait(until: {ci_green: "<PR url>"}, poll_every_sec: 300, timeout_sec: 7200, reason: "ждём CI") → DURABLE: waiting. Сервер разбудит, когда CI закончится (зелёный — условие выполнено; красный — «окончательно не выполнилось»).
3. Красный → разберись по логам (gh run view --log-failed), почини. PR неизменяемы: фикс — новой веткой от этой и НОВЫМ PR (старый закрой со ссылкой «superseded by»); если в репо работает pr-autofix и он уже открыл фикс-PR — используй его. Напечатай новую строку «PR: <url>» и снова жди CI.
4. Зелёный → убедись, что PR кто-то смержит, иначе следующий шаг «PR смержен» простоит сутки: если в CI репо есть свой мерж-джоб (job merge / merge queue) — ничего не делай; иначе gh pr merge <url> --auto --squash; если автомерж в репо запрещён — gh pr merge <url> --squash сразу (все чеки уже зелёные); если и это запрещено — одной строкой попроси владельца. Затем комментарий в issue, DURABLE: done.

Готово, когда: Все чеки PR зелёные (детерминированная проверка ci_green).
```

#### 10. PR смержен

```text
Тип шага: merged — Дождаться мержа (автомерж по зелёному CI или ручной) без траты модели.

Что происходит:
1. Детерминированный шаг: сервер каждые 5 минут проверяет, что PR смержен. Мерж запускает предыдущий шаг (ci-green): свой мерж-джоб репо, gh pr merge --auto --squash или прямой squash-мерж по зелёному CI.

Готово, когда: GitHub сообщает merged:true для PR этого плана.
```

#### 11. Деплой прошёл и живой

```text
Тип шага: deployed — Убедиться, что смерженный код реально задеплоен, а не «должен был».

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Как деплоится репозиторий: GitHub Actions на merge (gh run list --branch main), Cloudflare/Pages, VM-скрипт — посмотри README и workflows. Если деплоя нет (библиотека/доки) — так и скажи и заверши шаг.
2. Найди сигнал живой версии: /health с commit SHA, версия в ответе, статус workflow run для merge-коммита.
3. Ещё не задеплоено → task_item_wait(until: {http_ok: {url: "<health url>", contains: "<короткий SHA merge-коммита>"}} или {command_exit_zero: "gh run list --commit <sha> --json conclusion -q '.[0].conclusion' | grep -q success"}, timeout_sec: 7200, reason: "ждём деплой") → DURABLE: waiting.
4. Деплой упал → разберись, почини через новый PR (как в шаге CI) или сообщи владельцу.

Готово, когда: Есть доказательство, что в окружении работает именно эта версия (SHA/версия/успешный run).
```

#### 12. Подтвердить, что ошибка ушла в проде

```text
Тип шага: confirm-fixed — Баг закрыт не когда смержен фикс, а когда ошибка перестала появляться. Процесс ждёт ошибку: появилась — просыпается.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Если баг воспроизводился (R5) — прогони воспроизведение против прода/стейджинга: должно пройти.
2. Если ошибка видна в логах (R4 и ниже) — засыпай, ожидая её ПОВТОР после времени деплоя: task_item_wait(until: {command_exit_zero: "journalctl -u <svc> --since '<время деплоя>' | grep -q '<сигнатура>'"}, poll_every_sec: 600, timeout_sec: <2× обычный интервал появления, минимум 86400>, reason: "ждём, не вернётся ли ошибка") → DURABLE: waiting.
3. Проснулся по УСЛОВИЮ (ошибка вернулась) → фикс не помог: собери новый контекст и DURABLE: failed: ошибка вернулась <evidence> (план пойдёт в recovery / переоткроем).
4. Проснулся по ТАЙМАУТУ (ошибки нет всё окно) → подтверждено: DURABLE: done с интервалом наблюдения.

Лестница воспроизведения (R) — насколько надёжно мы видим проблему:
  • R5 — воспроизведено автоматически в песочнице/стейджинге одной командой (тест или скрипт)
  • R4 — наблюдается в логах (сгенерировать ошибку сами не можем)
  • R3 — есть чёткие шаги воспроизведения от пользователя
  • R2 — есть конкретный (не дефолтный) текст ошибки / exception
  • R1 — есть факт ошибки, привязанный ко времени и модулю, без деталей
  • R0 — записано со слов
  Правило: Цель — поднять R максимально до фикса. Фикс при R < 3 помечается как «спекулятивный» и обязательно получает шаг подтверждения в проде (наблюдение за логами).

Готово, когда: Воспроизведение проходит против реального окружения, или ошибка не появилась за окно наблюдения.
```

### Стадия «Архивация и разбор»

#### 13. Архивация: обновить живые доки и закрыть план

```text
Тип шага: archive — Сделанное становится источником истины: живые сценарии, лог требований, закрытый issue и сжатая память о решениях.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Живые сценарии: слей spec delta в docs/user-scenarios (сценарий описывает то, что есть сейчас, а не историю изменений).
2. docs/requirements-log.md: статусы (реализовано / отклонено с причиной / планируется).
3. Issue: итоговый комментарий (что сделано, PR, доказательства проверки, что осталось) и закрыть, если всё сделано; оставшееся — новыми issues.
4. Память: сжатая выжимка решений и граблей (что узнали, что не сработало) — дешёвой моделью в docs/changes/<дата>-<slug>.md или agent_store_artifact(type: decision); для багов — qa_log_register.
5. Предложи улучшение самого плейбука, если по ходу чего-то не хватало (в итоге шага).

Готово, когда: Живые сценарии и лог требований отражают новое состояние; issue закрыт/обновлён; выжимка решений сохранена.

Для этого плейбука:
- Для значимого бага — короткий blameless-разбор в issue: хронология, корневая причина, почему не поймали, что добавили (тест/алерт/проверку), чтобы класс ошибок не повторился.
- Зарегистрируй в QA-логах (qa_log_register), если доступно.
```
