# Плейбук `skill-tool` — Новый MCP-инструмент в доменном скиле

> Сгенерировано `scripts/build-playbooks.js` из `playbooks-src/skill-tool.json` и `library/step-types.json`. Правь источники, не этот файл.

**Когда:** Нужно добавить инструмент (MCP-тул) в существующий доменный скил (hh, sales, documents, freelance, speech, search): конвенции репо скила → файл и схема тула → исполняемый тест хендлера и регистрации → правило в промпт-домене → PR с зелёными CI и staging → деплой ядра → проверка в живой сессии. Обычную фичу или баг в продукте веди `feature`/`debugging`, новый модуль с нуля — `new-software`; изменение ядра или шлюза этот плейбук не покрывает.

**Результат:** Новый инструмент вызывается в живой сессии агента и возвращает ожидаемый ответ: виден в новой сессии, реальный вызов успешен, доки скила обновлены.

- Скил живёт отдельно от ядра: мерж его PR ещё не равно прод. Чекауты скилов на сервере синхронизируются только при деплое ядра, поэтому шаг «deployed» обязан доказать мерж-коммит в чекауте скила, а шаг «виден в новой сессии» — что его действительно подхватила новая сессия.
- Для интеграции/MCP runtime изменения укажи sandbox endpoint, реальные тестовые credentials/bindings по именам (без значений), input/output/logs, повтор/reset и production promotion в Environment Contract. Проведи разрешённый sandbox E2E; отказ тестировать только из-за возможной ошибки вреден. Не направляй тестовые вызовы в production.

**Запуск:** `playbook_run(playbook_id: "skill-tool", goal: "<что делаем>", vars: {repo: "<owner/repo>"})` → черновик плана → `task_update(status: "active")`.

### Стадия «Рамка: сценарий, контекст, сложность»

#### 1. Сценарий пользователя: ценность и шаги

```text
Тип шага: define-use-case — Зафиксировать, КАКУЮ ценность получает пользователь и через КАКИЕ шаги — это вход для тестов, песочницы и проверки результата.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Источник требований уже одобрен? Если цель ссылается на одобренную спецификацию/план (issue с утверждённой архитектурой и приёмкой, docs/spec.md) — НЕ выводи сценарий заново: сверь, что в ней есть ценность и шаги с EARS/Given-When-Then, сошлись на конкретные секции спецификации, и закрой шаг без полного прогона. Включай заново только реально недостающие пункты. Спецификация без ссылки на секции не считается сверенной.
2. Мини-ресерч ДО вопросов: найди в репозитории существующий сценарий на эту тему (docs/user-scenarios/, docs/requirements-log.md, соседние сценарии). Если он есть — дополняй его, а не пиши новый; если желание пользователя понятно из соседних историй — не мучай его анкетой, а скажи «нашёл сценарий X, понял так-то».
3. Ценность — как РЕЗУЛЬТАТ для конкретного актора, одной фразой. Может быть негативной. Примеры: «API-клиент получил ответ о цене товара»; «пользователь бесплатного тарифа не смог вызвать платную фичу»; «атакующий не получил кредов».
4. Оцени доказанность ценности по лестнице V (ниже) и запиши уровень с источником.
5. Шаги — хронологические шаги взаимодействия актора с системой до успеха, с указанием КОНКРЕТНЫХ функциональных блоков: экран/кнопка UI, эндпоинт API, команда CLI, MCP-тул, сообщение бота. Для каждого шага — ожидаемый результат в форме «КОГДА <событие> ТОГДА система <ответ>» (EARS / Given-When-Then).
6. Не-цели (что сознательно НЕ делаем) и крайние случаи (пустые данные, ошибка внешнего сервиса, повтор, права).
7. Если есть пробелы — ОДНО сообщение пользователю: ≤5 вопросов, у каждого твой рекомендуемый ответ («правильно ли я понял: …?»), плюс что улучшит фичу («если добавить X — будет сильно лучше»). Отправь и уйди в ожидание: task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопросы>) → DURABLE: waiting. Когда ответ придёт — шаг перезапустится с ним.
8. Запиши/обнови сценарий в docs/user-scenarios/<область>/<slug>.md целевого репозитория (или в итоге шага, если репозиторий ещё не выбран).

Лестница доказанности ценности (V) — насколько мы уверены, что это кому-то нужно:
  • V5 — есть явная ссылка, где ценность получают сейчас (платят / уже пользуются обходным путём)
  • V4 — много пользователей просят, есть документ custdev или поисковый спрос
  • V3 — есть отзывы / фича-реквесты от реальных пользователей
  • V2 — экспертная оценка сейлза/маркетолога, говорящего с клиентами (норм для средней фичи)
  • V1 — экспертная оценка инженера (норм для мелкой фичи)
  • V0 — не указано (норм только для нестрогой работы)
  Правило: Уровень не блокирует работу. Но если для нетривиальной фичи V ≤ 1 — ЯВНО скажи пользователю: «ценность не подтверждена, риск сделать не то» и предложи, что добавить, чтобы стало лучше.

Готово, когда: Записаны Ценность (с уровнем V) и Шаги с конкретными функциональными блоками и ожидаемыми результатами; открытые вопросы либо закрыты, либо явно помечены как риск.

Общее для плейбука «skill-tool»:
- Скил живёт отдельно от ядра: мерж его PR ещё не равно прод. Чекауты скилов на сервере синхронизируются только при деплое ядра, поэтому шаг «deployed» обязан доказать мерж-коммит в чекауте скила, а шаг «виден в новой сессии» — что его действительно подхватила новая сессия.
- Для интеграции/MCP runtime изменения укажи sandbox endpoint, реальные тестовые credentials/bindings по именам (без значений), input/output/logs, повтор/reset и production promotion в Environment Contract. Проведи разрешённый sandbox E2E; отказ тестировать только из-за возможной ошибки вреден. Не направляй тестовые вызовы в production.
```

#### 3. Сложность требований: флаги и челлендж

```text
Тип шага: requirements-complexity — Не тащить в реализацию требования, которые умножают сложность системы, без явного решения.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Если цель ссылается на одобренную спецификацию/план — требования и решения уже зафиксированы: сверь их и флаги с секцией спецификации, не переспрашивай пользователя и не выводи заново. Проверяй только реально новые/недостающие требования.
2. Выпиши требования списком (из сценария + неявные: права, платформы, данные, интеграции, производительность).
3. Каждому поставь флаг ⚪🟢🟡🔴⚫ (шкала ниже) с одной фразой «почему».
4. Для каждого 🔴 и ⚫ — челлендж: сколько новых состояний/веток × сценариев придётся тестировать, какие типичные баги, во сколько раз растёт система, какая дешёвая альтернатива даёт ту же ценность (например, вместо новой модели ролей — один флаг на профиле).
5. Проверь источник каждого требования: задача или реальное ограничение другой части системы. «Так уже написано» — не источник: такой код меняем, а не подстраиваемся.
6. Если есть 🔴/⚫ — одно сообщение пользователю с таблицей и рекомендацией → task_item_wait(awaiting_user: true, …) → DURABLE: waiting. Без 🔴/⚫ — сообщи коротко и иди дальше.
7. Итог: минимальный набор требований с флагами и принятые решения по 🔴/⚫.

Флаги сложности требований — чем выше флаг, тем больше требование плодит состояний, веток и тестов по всей системе:
  • ⚪ прозрачный — не меняет поведение/модель (текст, цвет, копирайт)
  • 🟢 зелёный — аддитивно и локально, один сценарий, без новых контрактов
  • 🟡 жёлтый — задевает общие контракты/схему данных/интеграцию/вторую платформу/производительность
  • 🔴 красный — модель доступа и прав, границы безопасности/аутентификации, биллинг, необратимая миграция данных, мульти-тенантность
  • ⚫ чёрный — неоднозначность: пересекающиеся сценарии с разным поведением, противоречия, неопределённые состояния
  Правило: 🔴 и ⚫ челленджим ВСЕГДА — и для себя, и для пользователя: во что обойдётся (сколько новых состояний × сценариев тестировать, какие баги типичны), какая дешёвая альтернатива даёт ту же ценность. Требование существует, только если идёт из задачи или из реального ограничения ДРУГОЙ части системы — «так уже написано» не источник требований. ⚫ разрешается до дизайна.

Готово, когда: Все требования помечены флагами; 🔴/⚫ либо сняты, либо явно подтверждены пользователем с пониманием цены; ⚫ разрешены.
```

```text

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Если цель ссылается на одобренную спецификацию/план — дизайн, срезы, план проверки и откат уже в ней: сверь, сошлись на секции и закрой коротко. Проектируй заново только недостающие части.

6. План проверки: каждый Шаг сценария → автотест или сценарий песочницы; целевой уровень S.
```

### Стадия «Песочница: сначала красный тест, потом код»

#### 6. Песочница: замкнутый цикл, который повторяет сценарий

```text
Тип шага: sandbox — Сделать так, чтобы агент сам, без человека, одной командой прогонял сценарий и видел результат — это главный ускоритель всей разработки (sandbox-driven development).

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Применимость (реши ДО постройки цикла): отдельным шагом песочница нужна, если цикл проверяет СУЩЕСТВУЮЩЕЕ поведение (баг/регрессия) или сценарий нельзя замкнуть внутри шага реализации. Для новой фичи, где первый срез реализации сам является красным циклом (red-tests-first, contract-тесты против мока внешнего сервиса), песочница отдельным шагом не нужна — цикл вплетается в implement, а его валидация `implementation_complete_and_sandbox_green` подтверждает, что первый срез был красным. Тогда закрой шаг ⏭/task_item_skip с причиной ДО старта; если шаг уже начат, а причина отмены — сужение области, закрывай task_item_exception с первой же попытки, не сжигая оставшиеся.
2. Выбери целевой уровень S (максимально достижимый при текущих доступах) и назови время цикла, которого хочешь добиться.
3. Построй цикл: тест/скрипт/харнесс, который проходит Шаги сценария через реальные функциональные блоки (API/CLI/UI-автоматизация), с фейками или sandbox-аккаунтами внешних зависимостей, фикстурами и сидом данных.
4. Одна команда запуска (например scripts/sandbox/<slug>.sh или конкретный npm test -- <file>), детерминированный вывод pass/fail.
5. Докажи цикл: запусти его СЕЙЧАС — он должен падать по правильной причине (фичи ещё нет / баг воспроизводится). Зелёный до изменений = песочница ничего не проверяет.
6. Если уровень S упирается в доступ — не жди внутри рана: попроси доступ у пользователя и task_item_wait(until: {credential_present: "<service>"} или awaiting_user) → DURABLE: waiting.
7. Закоммить песочницу (она часть результата) и опиши запуск в итоге шага.

Лестница автономности песочницы (S) — может ли агент сам замкнуть цикл «изменил → увидел результат»:
  • S5 — полный замкнутый цикл: агент сам поднимает окружение и прогоняет сценарий end-to-end за минуты (локально / эфемерно, внешние зависимости — фейки или песочницы провайдеров)
  • S4 — стейджинг с реальными зависимостями, куда агент сам деплоит и где сам наблюдает результат
  • S3 — автотесты с моками внешних зависимостей (unit/integration), без полного e2e
  • S2 — код запускается частично; внешние эффекты (прод-креды, железо, платежи) проверяет человек
  • S1 — только статический анализ/компиляция; поведение проверяет человек
  • S0 — нет исполнения вообще (код пишется вслепую)
  Правило: Скорость агента ≈ 1 / время замкнутого цикла без человека. Всегда целься в максимально достижимый S и явно называй его и время цикла. S4–S5 = «проект выглядит несложно, пилим».

Готово, когда: Одна команда прогоняет сценарий и сейчас падает по правильной причине; уровень S и время цикла записаны.

Для этого плейбука:
- Песочница — это тесты РЕПО СКИЛА, а не этого репо: сначала красный unit-тест хендлера (валидные и невалидные аргументы, пустой вход; ответ — объект, исключение не бросается) и красный тест регистрации (тул находится через реестр, имя и inputSchema совпадают), потом заготовка делает их зелёными.
- В целевом скиле нет тестового раннера — добавь минимальный `node --test` и скрипт `test` в package.json; шаг не пропускается.
- Одна команда запуска в корне скила, детерминированный pass/fail по exit-коду; до заготовки шаг обязан падать по правильной причине, зелёный до изменений = песочница ничего не проверяет.
```

### Стадия «Доставка и проверка в реальности»

#### 10. CI зелёный (ждём; чиним, если красный)

```text
Тип шага: ci-green — Довести PR до зелёного CI, не сидя в ране: ждём дёшево, просыпаемся, когда CI закончил.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Посмотри статус чеков PR (gh pr checks <url>).
2. Ещё идут → task_item_wait(until: {ci_green: "<PR url>"}, poll_every_sec: 300, timeout_sec: 7200, reason: "ждём CI") → DURABLE: waiting. Сервер разбудит, когда CI закончится (зелёный — условие выполнено; красный — «окончательно не выполнилось»).
3. Красный → разберись по логам (gh run view --log-failed), почини. PR неизменяемы: фикс — новой веткой от этой и НОВЫМ PR (старый закрой со ссылкой «superseded by»); если в репо работает pr-autofix и он уже открыл фикс-PR — используй его. Напечатай новую строку «PR: <url>» и снова жди CI.
4. Зелёный → убедись, что PR кто-то смержит, иначе следующий шаг «PR смержен» простоит сутки: если в CI репо есть свой мерж-джоб (job merge / merge queue) — ничего не делай; иначе gh pr merge <url> --auto --squash; если автомерж в репо запрещён — gh pr merge <url> --squash сразу (все чеки уже зелёные); если и это запрещено — одной строкой попроси владельца. Затем комментарий в issue, DURABLE: done.

Готово, когда: Все чеки PR зелёные (детерминированная проверка ci_green).

Для этого плейбука:
- Валидатор ci_and_staging_green, а не ci_green: правило владельца 2026-09-16 — мержу только когда зелёный И CI, И staging на актуальной версии PR; устаревший красный не закрывается молча.
- Ветка A: в .github/workflows/ci.yml целевого репо есть job staging-gate → жди оба через durable wait по ключу ci_and_staging_green с ссылкой на PR.
- Ветка B: job staging-gate отсутствует → шаг БЛОКИРУЕТСЯ и вешает владельцу задачу «добавить staging-gate в CI этого скила» (пробел ведём в issue #9), вместо того чтобы молча прогнать мимо. Никаких skip и continue-on-error без явного решения владельца; мерж поверх красного запрещён.
- Красное → разберись по логам; PR неизменяемы, фикс идёт новой веткой и новым PR (или через уже открытый autofix-PR). Устаревший конкретный тест в этом же PR можно заменить, назвав путь, причину, изменившееся требование и заменяющий исполняемый тест.
```

#### 12. Деплой прошёл и живой

```text

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

- Мерж в скил ≠ прод: чекауты скилов на сервере обновляются только при деплое ядра. После мержа запусти штатный деплой ядра (deploy-manual.yml в trained-assist-agent) — согласованный рестарт 2026-09-23 разрешён, он тихий, отложенные задачи поднимет новый процесс.
- Доказательство — что мерж-коммит стал предком HEAD чекаута скила на сервере: ssh vm "git -C /home/vova/agent-releases/<repo> merge-base --is-ancestor <merge-sha> HEAD" (exit 0 = дошло). Зелёный deploy-джоб и /health этого не доказывают: в healthе SHA ядра, а не скила.
- Запасной путь на случай снятия ssh-доступа (#1818): вывод деплой-workflow по конкретному merge-коммиту плюс явное подтверждение владельца в итоге шага. Не закрывай шаг «зелёным раном» без одного из двух и не уходи в вечное ожидание.
```

#### 13. Тул виден в новой сессии

```text

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Пройди Шаги сценария в проде/стейджинге через реальные функциональные блоки (API-запрос, CLI, UI-автоматизация, тестовое сообщение боту). Тестовый профиль, не реальные пользователи.
2. Сравни с ожидаемыми результатами «КОГДА … ТОГДА …» из сценария, по каждому шагу.
3. Проверь логи на новые ошибки после деплоя.
4. Не совпало → это баг: опиши (с R-уровнем) и DURABLE: failed: <что не так> — план не должен закрыться «по памяти».
5. Доказательства (ответы, скрины, выдержки логов) — в итог и комментарием в issue.

Готово, когда: Каждый Шаг сценария подтверждён в реальном окружении с доказательствами.

Для этого плейбука:
- Гейт «виден»: открой НОВУЮ сессию агента (не текущую) и проверь, что тул присутствует в списке MCP-инструментов целевого скила с тем же именем и схемой, что в файле.
- Текущие сессии его не видят — это норма, а не баг: MCP-серверы скилов стартуют на каждую сессию из чекаутов на сервере, поэтому тул появляется только после того, как деплой ядра синхронизировал скил.
- Не виден → план не закрывается: возвращайся к шагу деплоя (мерж-коммит не в чекауте или деплой не подтягал скил), а не помечай «виден» по памяти.
```

```text
Тип шага: verify-real — Пройти Шаги сценария там, где живёт пользователь: песочница → реальное окружение.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Пройди Шаги сценария в проде/стейджинге через реальные функциональные блоки (API-запрос, CLI, UI-автоматизация, тестовое сообщение боту). Тестовый профиль, не реальные пользователи.
2. Сравни с ожидаемыми результатами «КОГДА … ТОГДА …» из сценария, по каждому шагу.
3. Проверь логи на новые ошибки после деплоя.
4. Не совпало → это баг: опиши (с R-уровнем) и DURABLE: failed: <что не так> — план не должен закрыться «по памяти».
5. Доказательства (ответы, скрины, выдержки логов) — в итог и комментарием в issue.

Готово, когда: Каждый Шаг сценария подтверждён в реальном окружении с доказательствами.

- Гейт «вызван»: сделай живой вызов тула из новой сессии реальными (не тестовыми) аргументами и приложи ответ к итогу шага. Наличие в списке инструментов вызовом не считается — это два разных гейта, и оба обязательны.
- Нужны креды внешнего сервиса → task_item_wait(awaiting_user: true либо until credential_present) → DURABLE: waiting: ждём креды, вызов не фейкуем.
```

#### 15. Приёмка по принятым требованиям (независимый судья)

```text
Тип шага: verify-requirements — Ответить не «что сделано», а «соответствует ли результат принятым требованиям»: судья пересобирает доказательства сам и не верит отчёту исполнителя.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Сначала восстанови факты, а не память. Своё изменение найди по точной связи: `engineering_change_find(task_ref: "<issue/PR, который открывали>")` → `engineering_change_status(ref)`. За уже сделанное считается только exact-совпадение (названный номер, сохранённая связь `engineering_change_bind`, своя ветка) — похожий по теме чужой PR за твою работу не проходит.
2. Прочитай шесть фактов change_status (written / committed / pushed / merged / delivered / verified) и выполняй ТОЛЬКО недостающее. `satisfied` не переделывай; `unknown` — это «неизвестно», а не «не сделано»: сначала выясни, чем вызвано (CI недоступен, прод-эндпоинт чужой, нет доступа), и только потом решай, повторять ли. Никогда не повышай unknown до satisfied.
3. Позови судью: `engineering_verify(requirements_ref: "issue#<N>@<rev>", target: { pr | commit | branch | artifact }, scope: implementation | delivery | user_scenario)`. Требования — только принятые и закреплённые; не переписывай их под ответ. `run_checks` включай явно и только там, где команда запускается безопасно.
4. Исход решает, что дальше: verified → шаг закрыт, идти дальше. partial → ограниченный repair только по невыполненным требованиям (новая итерация плана), требования не переписывать. not_met → блокер: назови конкретное невыполненное требование и причину (внешняя блокировка / требование устарело / расходится намерение). inconclusive → это НЕ pass: собери недостающие evidence (то, что дало unknown) и повтори один раз; если evidence недоступен — зафиксируй это как блокирующее обстоятельство, а не как успех. Существенная продуктовая развилка (требования противоречат друг другу или «хочу не так») → верни вопрос владельцу и не закрывай план.
5. Applicability: если для этого типа результата проверка неприменима — закрой как not_applicable с основанием И альтернативным доказательством (docs-only: отрендеренная страница и ссылка вместо живого сценария; библиотека без деплоя: тест/потребление вместо health). Строка «не нужно» без альтернативного доказательства не считается.
6. Checkpoint: сохрани source refs и версии — requirements_ref, цель с закреплённой ревизией, commit sha, observed_at — в комментарии к issue/эпику и в итоге шага. Не копируй execution state плана.
7. Бюджеты попыток и ожиданий — у действующего runtime: своих циклов и повторов не заводи. Нужен долгий внешний сигнал (деплой, ответ владельца) → task_item_wait(...) и передай дальше.
8. Никогда не выдавай чужой PR за своё изменение и не подставляй «нет доступа» вместо «проверка не прошла»: ошибка авторизации — это ошибка доступа, а не отсутствие результата.

Готово, когда: Каждое принятое требование имеет вердикт судьи на закреплённой ревизии; verified ведёт дальше, остальное — конкретное действие (ограниченный repair, блокер с причиной, вопрос владельцу, ожидание runtime), и ни одно требование не закрыто «по памяти».

Для этого плейбука:
- Приёмка нового тула = принятые требования к нему (что делает, контракт, что НЕ делает) на merge-коммите. Судья сверяет их независимо от двух предыдущих гейтов: «тул виден» и «тул вызван» доказывают факт вызова, а не соответствие требованиям.
- Требования берутся из issue карточки. Если их там нет — зафиксируй это как блокер приёмки (без принятых требований приёмка невозможна), а не подставь вместо них описание из шага проектирования.
```

#### 16. Архивация: доставить живые доки и закрыть план

```text
Тип шага: archive — Проверенное изменение становится источником истины: живые доки доставлены тем путём, который реально работает, issue закрыт, решения сохранены.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Сначала объяви исход архивации — merged (PR уже смержен), delivered (изменение доставлено без git-PR: доки, внешний артефакт) или deferred (доки сознательно вне объёма). Исход запиши в evidence шага; он определяет, как доставляются доки.
2. Reconciliation receipt (#135): до любого заявления про живые доки заполни receipt по контракту contracts/reconciliation-receipt.schema.json и проверь его `npm run report:reconciliation -- <файл>` (--strict — если хочешь ненулевой код на нечестный receipt). В receipt: plan/шаг, принятые требования (ref + revision), target commits, delta ADDED/MODIFIED/REMOVED с per-REQ refs и target.kind, code_delivery (merged|delivered|unknown), baseline (applied|pending|not_applicable|conflict) с commit и paths, missing_requirements, followups. Текст инструкции без заполненного receipt — не сверка.
3. Две стадии — отдельно, никогда не сливай в одно «готово»: код доставлен (code_delivery) и baseline обновлён (baseline) — разные факты с разными доказательствами. Состояние «код смержен, доки ещё pending» — нормальное и честное: пиши в issue оба факта, а «доки обновлены» не заявляй до мержа docs-PR (applied) или явного not_applicable с причиной.
4. Куда пишем дельту: изменение поведения → target.kind spec или contract; границы, инварианты, принятые решения → architecture или adr. Отклонённые, deferred и невыполненные пункты в as-built не выдавай — они либо missing_requirements, либо followup с ref на issue. Всё TODO в архитектуру не превращай.
5. Существование файла ≠ применение дельты: в applied перечислены реальные paths, и дельта видна в них на указанном baseline commit. Не применённые пункты → baseline pending + followup, а не молчаливый applied.
6. merged: живые доки (spec delta в цель, объявленную в propose-change: contracts, ADR, docs — см. следующий пункт) слей в ТОМ ЖЕ PR до мержа. После мержа ветка мертва — правь только issue и ссылки, новых коммитов в смерженную ветку не делай. Не успел до мержа — переходи к delivered.
7. delivered: доки не попали в основной PR — открой отдельный docs-only PR с пометкой deferred и ссылкой на исходный PR (приоритет всё же у до-мержевой доставки в основном PR). Живым считается только доставленный baseline, не обещание.
8. deferred: доки не нужны — одной строкой в issue: «docs: not applicable — <причина>». Не создавай пустую форму ради заполнения.
9. Цель слияния дельты — та, что объявлена в propose-change (её target), а не только docs/user-scenarios: этот каталог дефолт, но не единственный путь (#47). docs/user-scenarios/: пиши туда, только если в целевом репозитории уже есть этот раздел с живыми сценариями. Нет раздела — не создавай каталог ради шага; сошлись на объявленную в propose-change цель.
10. Повтор шага не плодит второй PR и не дублирует требования: если receipt по этому плану уже опубликован, не создавай новый архивный PR ради того же — дополни его (docs follow-up с ref на существующий receipt) или зафиксируй, что дельта не изменилась (baseline not_applicable с причиной).
11. Статус требований — в issues (правило владельца 2026-09-28), не в docs/requirements-log.md: обнови/закрой issue, оставшееся вынеси новыми issues. requirements-log.md — история, а не текущий статус.
12. Issue: итоговый комментарий (что сделано, PR, доказательства проверки, что осталось) и закрытие, если всё сделано.
13. Память: сжатая выжимка решений и граблей (что узнали, что не сработало) — дешёвой моделью в docs/changes/<дата>-<slug>.md или agent_store_artifact(type: decision); для багов — qa_log_register.
14. Предложи улучшение самого плейбука, если по ходу чего-то не хватало (в итоге шага).

Готово, когда: Исход архивации объявлен; reconciliation receipt заполнен по контракту и проверен (code_delivery и baseline видны раздельно); живые доки доставлены в объявленную propose-change цель (в PR до мержа, отдельным docs-PR или явным not_applicable); ни одна дельта не заявлена applied без реальных paths; статус требований отражён в issue; выжимка решений сохранена.
```
