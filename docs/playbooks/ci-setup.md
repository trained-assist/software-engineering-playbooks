# Плейбук `ci-setup` — Настройка ручного прогона тестов в репозитории

> Сгенерировано `scripts/build-playbooks.js` из `playbooks-src/ci-setup.json` и `library/step-types.json`. Правь источники, не этот файл.

**Когда:** Репозиторию нужен ручной запуск полного набора тестов для ветки (workflow_dispatch), а его нет или непонятно, есть ли. Разовый и идемпотентный: настроенном репозитории второй запуск ничего не меняет.

**Результат:** В репозитории есть команда «прогнать полный набор тестов для любой ветки»: настроено один раз, повторный запуск отвечает «уже настроено».

- Изменение идёт PR-ом в целевой репозиторий (ветка плана, база origin/main). Ничего не сливается и не выкатывается этим плейбуком — только настройка ручного запуска.
- Если шаг ci-setup ответил «уже настроено» — стадию PR целиком закрой одной строкой «⏭ не нужно — уже настроено», не открывая ничего.
- Порядок важен: сначала правка workflow и её проверка, потом PR, потом ожидание CI, потом мерж. Шаги пропускай только с явной причиной.
- Человек может не знать GitHub Actions: последний шаг обязан объяснить простыми словами, что появилось и как это запустить.

**Запуск:** `playbook_run(playbook_id: "ci-setup", goal: "<что делаем>", vars: {repo: "<owner/repo>"})` → черновик плана → `task_update(status: "active")`.

## Шаги подробно

### Стадия «Разбор репозитория и настройка workflow»

#### 1. Настроить ручной прогон тестов в репозитории

```text
Тип шага: ci-setup — Один раз дать репозиторию команду «прогнать полный набор тестов для любой ветки» — без PR и без локального прогона. Повторный запуск отвечает «уже настроено».

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Стек и что уже есть: по package.json / pyproject.toml / requirements.txt / go.mod определи стек; ls .github/workflows — перечисли существующие workflow и их триггеры. Всё это — списком в ИТОГЕ ШАГА.
2. Идемпотентность (наблюдаемо): есть активный workflow с workflow_dispatch, который гоняет тесты и ничего не сливает и не выкатывает → ответ «уже настроено», PR НЕ открывай, стадию PR дальше закрой одной строкой.
3. Иначе выбери минимальную правку: (а) есть ci.yml без dispatch → добавить блок workflow_dispatch ТОЛЬКО если все тяжёлые джобы и так привязаны к push/pull_request; (б) по умолчанию — отдельный .github/workflows/manual-tests.yml из templates/ci.yml, он не трогает PR-пайплайн; (в) CI нет вовсе — создать manual-tests.yml из того же шаблона.
4. Шаблон templates/ci.yml — рабочая заготовка: workflow_dispatch с input ref (ветка под тестом) и опциональным input suite, checkout с ref: inputs.ref, своя concurrency-группа manual-tests-<ref> только на ручные запуски. Команды тестов другого стека — по примерам в шапке шаблона.
5. Правило безопасности: в добавленном workflow не должно быть шагов сливания и выкатки и не должно быть continue-on-error. Существующий чужой ci.yml не переписывай целиком — только добавь блок dispatch, если условие (а) выполнено.
6. Сделай правку в ветке этого плана и сразу закоммить; прогони быстрые проверки локально (syntax-check, валидность YAML).
7. Если workflow есть, но input ref отсутствует — добавь его: без него ветку прогнать нельзя.
8. В итоге — какие файлы добавлены/изменены и почему повторный запуск скажет «уже настроено».

Готово, когда: В репозитории есть активный workflow с workflow_dispatch и input ref, запускающий полный набор тестов ветки и не выполняющий сливание/выкатку — либо явное «уже настроено», если он был и раньше.

Общее для плейбука «ci-setup»:
- Изменение идёт PR-ом в целевой репозиторий (ветка плана, база origin/main). Ничего не сливается и не выкатывается этим плейбуком — только настройка ручного запуска.
- Если шаг ci-setup ответил «уже настроено» — стадию PR целиком закрой одной строкой «⏭ не нужно — уже настроено», не открывая ничего.
- Порядок важен: сначала правка workflow и её проверка, потом PR, потом ожидание CI, потом мерж. Шаги пропускай только с явной причиной.
- Человек может не знать GitHub Actions: последний шаг обязан объяснить простыми словами, что появилось и как это запустить.
```

### Стадия «PR: открыть, довести до зелёного, слить»

#### 2. Открыть PR

```text
Тип шага: open-pr — Отдать изменение на CI и ревью одним связным PR с доказательствами.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Перед пушем: ветка твоя (создана в этом плане), не main/master, нет открытого PR на эту ветку (PR неизменяемы — правки после открытия идут новой веткой и новым PR).
2. git push -u origin <ветка>; gh pr create с телом: ссылка на issue, сценарий, что изменено, доказательства песочницы (до: красный, после: зелёный), план проверки, риски/откат.
3. Если в репозитории принят checklist.md — добавь цель и три пункта (CI green / merged / deployed) со ссылкой на PR.
4. Комментарий в issue со ссылкой на PR.
5. В итоге шага ОТДЕЛЬНОЙ строкой: PR: https://github.com/<owner>/<repo>/pull/<n> — по ней следующие шаги (CI, merge) найдут PR автоматически.

Готово, когда: PR открыт, ссылка напечатана строкой «PR: <url>».
```

#### 3. CI зелёный (ждём; чиним, если красный)

```text
Тип шага: ci-green — Довести PR до зелёного CI, не сидя в ране: ждём дёшево, просыпаемся, когда CI закончил.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Посмотри статус чеков PR (gh pr checks <url>).
2. Ещё идут → task_item_wait(until: {ci_green: "<PR url>"}, poll_every_sec: 300, timeout_sec: 7200, reason: "ждём CI") → DURABLE: waiting. Сервер разбудит, когда CI закончится (зелёный — условие выполнено; красный — «окончательно не выполнилось»).
3. Красный → разберись по логам (gh run view --log-failed), почини. PR неизменяемы: фикс — новой веткой от этой и НОВЫМ PR (старый закрой со ссылкой «superseded by»); если в репо работает pr-autofix и он уже открыл фикс-PR — используй его. Напечатай новую строку «PR: <url>» и снова жди CI.
4. Зелёный → убедись, что PR кто-то смержит, иначе следующий шаг «PR смержен» простоит сутки: если в CI репо есть свой мерж-джоб (job merge / merge queue) — ничего не делай; иначе gh pr merge <url> --auto --squash; если автомерж в репо запрещён — gh pr merge <url> --squash сразу (все чеки уже зелёные); если и это запрещено — одной строкой попроси владельца. Затем комментарий в issue, DURABLE: done.

Готово, когда: Все чеки PR зелёные (детерминированная проверка ci_green).
```

#### 4. PR смержен

```text
Тип шага: merged — Дождаться мержа (автомерж по зелёному CI или ручной) без траты модели.

Что происходит:
1. Детерминированный шаг: сервер каждые 5 минут проверяет, что PR смержен. Мерж запускает предыдущий шаг (ci-green): свой мерж-джоб репо, gh pr merge --auto --squash или прямой squash-мерж по зелёному CI.

Готово, когда: GitHub сообщает merged:true для PR этого плана.
```

### Стадия «Проверка и объяснение простыми словами»

#### 5. Проверка сценария в реальном окружении

```text
Тип шага: verify-real — Пройти Шаги сценария там, где живёт пользователь: песочница → реальное окружение.

Репозиторий: {repo} (если вместо имени репозитория тут слово repo в фигурных скобках — его не передали в playbook_run: определи из цели и итогов прошлых шагов или спроси пользователя).

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Пройди Шаги сценария в проде/стейджинге через реальные функциональные блоки (API-запрос, CLI, UI-автоматизация, тестовое сообщение боту). Тестовый профиль, не реальные пользователи.
2. Сравни с ожидаемыми результатами «КОГДА … ТОГДА …» из сценария, по каждому шагу.
3. Проверь логи на новые ошибки после деплоя.
4. Не совпало → это баг: опиши (с R-уровнем) и DURABLE: failed: <что не так> — план не должен закрыться «по памяти».
5. Доказательства (ответы, скрины, выдержки логов) — в итог и комментарием в issue.

Готово, когда: Каждый Шаг сценария подтверждён в реальном окружении с доказательствами.

Для этого плейбука:
- Здесь «реальное окружение» — это GitHub Actions целевого репозитория после мержа: workflow виден на вкладке Actions, у него есть input ref, запуск с веткой стартует и заканчивается (любым результатом — сам прогон, не его цвет, здесь и проверяем).
- Финальный ответ владельцу — простыми словами, без терминов: что появилось (одна команда «прогнать тесты этой ветки»), как её запустить (Actions → manual-tests → Run workflow → ветка), и что запуск только проверяет: ничего не сливает в main и ничего не выкатывает.
```
