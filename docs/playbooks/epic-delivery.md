# Плейбук `epic-delivery` — Довести эпик/план архитектуры до конца (мета-цикл)

> Сгенерировано `scripts/build-playbooks.js` из `playbooks-src/epic-delivery.json` и `library/step-types.json`. Правь источники, не этот файл.

**Когда:** Есть эпик и единый план архитектуры с карточками (IMPLEMENTATION-AND-INTEGRATION-PLAN.md) и чек-листом приёмки; нужно автономно, в том числе ночью, пройти карточку за карточкой: дочерний инженерный план с песочницей → независимое кросс-ревью другой семьёй моделей → обновление плана → следующая карточка, и в конце — приёмка по чек-листу.

**Результат:** Все карточки плана доставлены дочерними планами с песочницей и приняты независимым ревью, план архитектуры отражает реальность после каждой итерации, чек-лист приёмки прогнан с отчётом.

- Цикл без конструкции повтора: одна итерация = «Следующая карточка → Дочерний план → Кросс-ревью → Обновление плана → Цикл или финиш»; последний шаг дописывает копию итерации сразу после себя (task_item_add), пока есть карточки и бюджет итераций.
- Строит Claude (developer · doctor), проверяет другая семья моделей (reviewer · doctor → Codex, запасной OpenCode doctor). Кросс-ревью не правит код — только вердикт и замечания.

**Запуск:** `playbook_run(playbook_id: "epic-delivery", goal: "<что делаем>", vars: {epic: "<URL эпик-issue>", arch_repo: "<owner/repo>", max_iterations: 8})` → черновик плана → `task_update(status: "active")`.

## Шаги подробно

### Стадия «Подготовка эпика»

#### 1. Предполётная проверка эпика и журнал итераций

```text
Тип шага: epic-preflight — Перед автономным ночным циклом убедиться, что он вообще может дойти до конца (карточки понятны, мержи и деплой возможны, независимый ревьюер доступен), и завести журнал итераций на эпике — чтобы цикл можно было продолжить после любого сбоя.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Прочитай в репозитории архитектуры документ плана (карточки, их статусы и зависимости), чек-лист приёмки и DECISIONS.md. Выпиши список карточек: id, название, целевой репозиторий (или «новый»), зависимости, текущий статус. Новых документов-планов НЕ заводи — план один.
2. Эпик-issue обязателен и передаётся на входе: открой его (gh issue view). Если его нет или он закрыт — это блокер, эпик не создавай сам.
3. Проверь предусловия цикла для каждого существующего целевого репозитория открытых карточек: есть CI и staging/деплой (без них дочерний план не сможет смержить и проверить), у агента есть доступ на запись. Для карточек «новый репозиторий» — что new-software сможет его завести (права на организацию).
4. Проверь, что независимый ревьюер доступен: шаг кросс-ревью идёт ролью reviewer на уровне doctor, это другая семья моделей (Codex, запасной — OpenCode doctor, не Claude). Если движок Codex сейчас недоступен — отметь это в журнале как риск (ревью уйдёт на запасной движок), это не блокер.
5. Заведи или обнови на эпике ОДИН комментарий «Журнал итераций» (найди существующий по заголовку, не плоди дубли; обновляй через gh api PATCH): таблица карточка | статус | дочерний план | вердикт ревью | PR плана + параметры цикла (бюджет итераций, id этого плана).
6. Блокеры, которые может снять только владелец (нет доступа/секрета, необратимое действие, дорогая развилка архитектуры): ОДИН вопрос с твоей рекомендацией и вариантами через task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопрос + рекомендация>). Всё остальное решай сам как архитектор и записывай решение с обоснованием в журнал.

Готово, когда: Список карточек со статусами и зависимостями собран, предусловия проверены (или единственный вопрос владельцу задан и отвечен), журнал итераций на эпике существует.

Общее для плейбука «epic-delivery»:
- Цикл без конструкции повтора: одна итерация = «Следующая карточка → Дочерний план → Кросс-ревью → Обновление плана → Цикл или финиш»; последний шаг дописывает копию итерации сразу после себя (task_item_add), пока есть карточки и бюджет итераций.
- Строит Claude (developer · doctor), проверяет другая семья моделей (reviewer · doctor → Codex, запасной OpenCode doctor). Кросс-ревью не правит код — только вердикт и замечания.
```

### Стадия «Итерация: карточка → песочница → кросс-ревью → план»

#### 2. Следующая карточка плана

```text
Тип шага: next-card — Выбрать одну следующую карточку, у которой закрыты все зависимости, и зафиксировать выбор с причиной — или честно сказать, что карточек не осталось.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Перечитай АКТУАЛЬНЫЕ документ плана (main репозитория архитектуры — прошлая итерация могла его поменять) и журнал итераций на эпике.
2. Кандидаты: карточки не в статусе «сделано», все зависимости которых сделаны; карточка, отклонённая ревью, или новая карточка из блокирующих замечаний — тоже кандидат. Из кандидатов выбери одну: сначала разблокирующие больше всего следующих, потом меньший риск.
3. Определи вид работы: новый репозиторий/сервис → new-software; изменение в существующем → feature; дефект из ревью → debugging. Выпиши строки чек-листа приёмки, которые эта карточка должна закрыть.
4. Запиши выбор комментарием на эпике (карточка, почему она, вид работы, строки приёмки) и обнови строку в журнале итераций (статус «в работе»).
5. Если кандидатов нет, а незакрытые карточки есть (всё заблокировано) — это развилка: реши сам, что разблокировать, или, если это необратимо/дорого, один вопрос владельцу с рекомендацией через task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопрос + рекомендация>).
6. Если незакрытых карточек не осталось — запиши на эпике «все карточки закрыты», а оставшиеся шаги ЭТОЙ итерации (дочерний план, кросс-ревью, обновление плана) пропусти через task_item_skip с этой причиной; шаг «Цикл или финиш» завершит цикл.

Готово, когда: На эпике записана выбранная карточка с причиной, видом работы и строками приёмки — или «все карточки закрыты» и шаги итерации пропущены.
```

#### 3. Дочерний инженерный план карточки

```text
Тип шага: child-plan — Карточку делает отдельный инженерный план с песочницей (new-software / feature / debugging) в фоне; мета-план только запускает его, спит до его конца и записывает исход. Сам работу дочернего плана не делает.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Идемпотентность: сначала проверь журнал итераций и итоги этого шага — если для этой карточки дочерний план уже запущен (есть task id), НЕ запускай второй, переходи к ожиданию/чтению исхода.
2. Если прошлый шаг записал «все карточки закрыты» — пропусти себя (task_item_skip) с этой причиной.
3. Запусти дочерний план: playbook_run(playbook_id: <new-software|feature|debugging по выбору прошлого шага>, activate: true, vars: {repo: <owner/name целевого репозитория; для нового — не передавай>}, goal: <id и название карточки + что сделать + строки чек-листа приёмки дословно + ссылка на эпик + правило «решения принимает архитектор по плану и DECISIONS.md; владельца не спрашивать, кроме необратимых действий и дорогих развилок архитектуры»>).
4. Запиши task id дочернего плана комментарием на эпике и в журнал итераций.
5. Усни до конца дочернего плана: task_item_wait(until: {task_done: "<task id дочернего плана>"}, poll_every_sec: 600, timeout_sec: 259200, reason: "ждём дочерний план карточки") → DURABLE: waiting. Не опрашивай в цикле и не делай работу дочернего плана сам.
6. После пробуждения прочитай исход через task_get(<task id>): done / failed / cancelled, PR и их мерж, итог песочницы и проверки в реальном окружении, последняя ошибка. Запиши исход на эпике и в журнал. Провал дочернего плана — не провал этого шага: его разберёт кросс-ревью.

Готово, когда: Дочерний план запущен ровно один раз, дошёл до конца (done / failed / cancelled или таймаут ожидания), исход с PR и доказательствами записан на эпике.
```

#### 4. Независимое кросс-ревью (другая семья моделей)

```text
Тип шага: cross-review — Claude строит — Codex проверяет «с другой стороны». Роль reviewer на уровне doctor в рантайме означает независимое ревью другой семьёй моделей, чем у исполнителя-Claude: Codex, запасной — OpenCode doctor, никогда не Claude. Ревьюер сверяет сделанное дочерним планом с приёмкой карточки, инвариантами и чек-листом и выносит вердикт; код сам не переписывает.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Если прошлые шаги записали «все карточки закрыты» — пропусти себя (task_item_skip).
2. Собери, что поставил дочерний план: его task (task_get), смерженные PR и их диффы (gh pr diff), команду песочницы и её вывод, доказательства проверки в реальном окружении (логи, URL, ответы), issue дочернего плана.
3. Сверь с: критериями карточки в документе плана, строками чек-листа приёмки для этой карточки, инвариантами INV-* и решениями DECISIONS.md репозитория архитектуры. Проверяй по доказательствам, а не по словам итога: запусти песочницу/тесты сам, если это возможно без записи в прод.
4. Вынеси вердикт: accept / accept-with-followups / reject. Замечания пронумеруй; у каждого — блокирующее или нет, где (файл/PR/строка), почему, что сделать. Проваленный или отменённый дочерний план — reject с причиной.
5. Опубликуй ревью ОДНИМ комментарием на эпике с заголовком «Кросс-ревью <карточка>: <вердикт>» (кто ревьюировал — модель/движок) и поставь ссылку на него в журнал итераций.
6. Блокирующие замечания заведи issues в целевых репозиториях (ссылка на ревью и карточку) — шаг обновления плана превратит их в карточки. Код сам не правь и PR не открывай.

Готово, когда: На эпике опубликован комментарий кросс-ревью с вердиктом и пронумерованными замечаниями (блокирующее/нет), ссылка в журнале, блокирующие замечания заведены issues.
```

#### 5. Обновление плана архитектуры по итогам ревью

```text
Тип шага: architecture-update — Архитектор применяет ревью к единственному плану: статус карточки, следующие шаги, отметки приёмки и изменившиеся решения — через PR с CI и мержем, чтобы следующая итерация выбирала по актуальному плану.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Если прошлые шаги записали «все карточки закрыты» — пропусти себя (task_item_skip).
2. Прочитай вердикт кросс-ревью и исход дочернего плана. Реши как архитектор: accept → карточка «сделано»; accept-with-followups → «сделано» + follow-up карточки; reject → карточка обратно в работу с блокирующими замечаниями как критериями (или новые карточки на них).
3. Обнови ТОЛЬКО существующий документ плана: статус карточки, ссылки на PR/ревью, следующие шаги и зависимости, которые ревью поменяло. Новых документов-планов не создавай.
4. В чек-листе приёмки отметь строки, закрытые с доказательством (ссылка на PR/лог/ревью); строки без доказательства не отмечай.
5. Если решение поменялось — допиши запись в DECISIONS.md (что, почему, ссылка на ревью). Дорогую или необратимую развилку — один вопрос владельцу с рекомендацией через task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопрос + рекомендация>); остальное решай сам.
6. Ветка → PR в репозиторий архитектуры → дождись CI → смержи (gh pr merge --squash; пока CI идёт — task_item_wait(until: {ci_green: "<PR url>"}, poll_every_sec: 300, timeout_sec: 7200, reason: "ждём CI плана"), а не опрос в цикле). В итоге шага — URL PR.
7. Обнови журнал итераций на эпике: статус карточки, вердикт, PR плана.

Готово, когда: PR с обновлённым планом (и чек-листом/DECISIONS при необходимости) смержен, журнал итераций на эпике отражает новый статус карточки.
```

#### 6. Цикл или финиш

```text
Тип шага: loop-or-finish — Повторов в плане нет — цикл делается легальной самоправкой: пока карточки есть и бюджет итераций не исчерпан, шаг дописывает в этот же план следующую итерацию сразу после себя.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Посчитай номер текущей итерации по журналу на эпике (сколько раз был выбран «Следующая карточка») и прочитай бюджет итераций.
2. Есть ли незакрытые карточки в актуальном плане (main репозитория архитектуры) и не записано ли «все карточки закрыты»?
3. Если карточки есть и бюджет не исчерпан: прочитай текущий план через task_get (этот task id), возьми пункты последней итерации — «Следующая карточка», «Дочерний инженерный план карточки», «Независимое кросс-ревью», «Обновление плана архитектуры», «Цикл или финиш» — и добавь их копии цепочкой через task_item_add: первый с after_item_id = id ЭТОГО пункта, каждый следующий — after_item_id предыдущего добавленного. Контракт копируй без изменений: title (+ « — итерация N»), stage, execution_kind, executor_role, minimum_model_level, context_budget, validation, instructions.
4. Проверь через task_get, что 5 новых пунктов стоят сразу после этого шага и перед финальной приёмкой, в правильном порядке.
5. Иначе — финиш: причина (все карточки закрыты / исчерпан бюджет итераций — тогда список оставшихся карточек). Ничего не добавляй; дальше пойдёт финальная приёмка.
6. Запиши решение (следующая итерация N / финиш и почему) комментарием на эпике и в журнал.

Готово, когда: Следующая итерация добавлена цепочкой сразу после этого шага с теми же контрактами — или записан финиш с причиной.
```
