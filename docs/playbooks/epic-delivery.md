# Плейбук `epic-delivery` — Довести эпик/план архитектуры до конца (мета-цикл)

> Сгенерировано `scripts/build-playbooks.js` из `playbooks-src/epic-delivery.json` и `library/step-types.json`. Правь источники, не этот файл.

**Когда:** Есть эпик, единый план архитектуры (IMPLEMENTATION-AND-INTEGRATION-PLAN.md — структура и зависимости) и GitHub Project, где у каждой карточки есть issue со статусом и чек-листом приёмки; нужно автономно, в том числе ночью, пройти карточку за карточкой: дочерний инженерный план с песочницей → независимое кросс-ревью другой семьёй моделей → обновление плана → следующая карточка, и в конце — приёмка по чек-листам из issues эпиков и карточек.

**Результат:** Все карточки плана доставлены дочерними планами с песочницей и приняты независимым ревью, статусы в GitHub Project и чек-листы в issues карточек отражают реальность после каждой итерации, чек-листы приёмки эпиков и карточек прогнаны с отчётом.

- Цикл без конструкции повтора: одна итерация = «Следующая карточка → Дочерний план → Кросс-ревью → Обновление плана → Цикл или финиш»; последний шаг дописывает копию итерации сразу после себя (task_item_add), пока есть карточки и бюджет итераций.
- Карточки строят дочерние планы на OpenCode (их шаги master/bachelor); если OpenCode дважды провалил шаг по качеству — третья попытка на Claude (escalate_to_doctor). Claude (doctor) — только архитектурные шаги мета-цикла: предполётная проверка, выбор карточки, обновление статусов/плана, приёмка. Проверяет другая семья моделей (reviewer · doctor → Codex, запасной OpenCode doctor). Кросс-ревью не правит код — только вердикт и замечания.

**Запуск:** `playbook_run(playbook_id: "epic-delivery", goal: "<что делаем>", vars: {epic: "<URL эпик-issue>", arch_repo: "<owner/repo>", project: "https://github.com/orgs/<org>/projects/<n>", max_iterations: 8})` → черновик плана → `task_update(status: "active")`.

|---|---|---|---|---|---|
| 1 | Подготовка эпика | Предполётная проверка эпика и журнал итераций | `epic-preflight` | developer · doctor (Claude (дорого)) · large | `epic_preflight_passed_and_ledger_written` |
| 2 | Итерация: карточка → песочница → кросс-ревью → план | Следующая карточка плана | `next-card` | developer · doctor (Claude (дорого)) · medium | `iteration_card_recorded_once_with_marker` |

| 4 | Итерация: карточка → песочница → кросс-ревью → план | Независимое кросс-ревью (другая семья моделей) | `cross-review` | reviewer · doctor (Codex — другая семья моделей, не Claude) · large | `verdict_for_this_iteration_child_published_or_continuation_added` |

## Шаги подробно

### Стадия «Подготовка эпика»

#### 1. Предполётная проверка эпика и журнал итераций

```text
Тип шага: epic-preflight — Перед автономным ночным циклом убедиться, что он вообще может дойти до конца (карточки и их issues понятны, мержи и деплой возможны, независимый ревьюер доступен), и завести журнал итераций на эпике — чтобы цикл можно было продолжить после любого сбоя.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; GitHub Project: {project}; чек-листы приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, https://github.com/orgs/trained-assist/projects/1 (org trained-assist, номер 1), «чек-листы в issues эпиков и карточек», 8. Источник правды: статус карточек и чек-листы приёмки берутся из Project и issue карточки (gh project item-list <номер> --owner <org> --format json --limit 500; gh issue view <url> --json title,body,state,comments); поля Project: Status (Draft/Ready/In progress/Verification/Blocked/Done), Stage (R00, I00…I10, Ops), Card, Target repo, Depends on, Sandbox; статус меняй через gh project item-edit (id поля и опций — gh project field-list <номер> --owner <org> --format json). ПЕРЕД любой работой по карточке найди её issue в {arch_repo}: заголовок начинается с id карточки (gh issue list -R <репозиторий архитектуры> --state all --search "<id> in:title"). Если он есть — это исходное ТЗ: используй как есть, не переписывай и не изобретай заново (дополнить можно комментарием). Если нет — создай по шаблону: заголовок «<id> — <название>», тело = текст карточки из плана + чек-лист приёмки task list'ом (- [ ] …); сделай sub-issue эпика своей стадии (gh api repos/<репозиторий>/issues/<номер эпика>/sub_issues -F sub_issue_id=<числовой id issue>) и добавь в Project (gh project item-add) с полями Card, Stage, Target repo, Depends on, Sandbox и Status «Draft» или «Ready». Владелец и другие агенты заводят и уточняют issues параллельно — сначала смотри, готов ли issue, не трать время на изобретение. Старые баги из trained-assist-agent в Project не переносить. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Список карточек и их статусы — из GitHub Project (gh project item-list <номер> --owner <org> --format json --limit 500): id (поле Card или префикс заголовка), название, Status, Stage, Target repo (или «новый»), Depends on, Sandbox, ссылка на issue. Зависимости — из поля Depends on; если оно пустое или спорное — из графа стадий и зависимостей в документе плана (main репозитория архитектуры). Прочитай DECISIONS.md. Статусы в документе плана не ищи и не веди; новых документов-планов НЕ заводи — план один.
2. Сверь карточки плана с Project: у каждой карточки должен быть issue «<id> — <название>» (sub-issue эпика своей стадии, в Project). Сначала ищи готовый (gh issue list --search, в том числе в эпиках стадий) — владелец и другие агенты заводят их параллельно; найденный не переписывай. Недостающие — заведи по шаблону из правил выше. Выпиши, каких issues не хватало и что заведено.
3. Эпик-issue обязателен и передаётся на входе: открой его (gh issue view). Если его нет или он закрыт — это блокер, эпик не создавай сам.
4. Проверь предусловия цикла для каждого существующего целевого репозитория открытых карточек: есть CI и staging/деплой (без них дочерний план не сможет смержить и проверить), у агента есть доступ на запись. Для карточек «новый репозиторий» — что new-software сможет его завести (права на организацию). Проверь, что у агента есть права на запись в Project (gh project field-list <номер> --owner <org> отвечает, статус можно поменять).
5. Проверь, что независимый ревьюер доступен: шаг кросс-ревью идёт ролью reviewer на уровне doctor, это другая семья моделей (Codex, запасной — OpenCode doctor, не Claude). Если движок Codex сейчас недоступен — отметь это в журнале как риск (ревью уйдёт на запасной движок), это не блокер.
6. Заведи или обнови на эпике ОДИН комментарий «Журнал итераций» (найди существующий по заголовку, не плоди дубли; обновляй через gh api PATCH): таблица карточка (ссылка на issue) | статус в Project | дочерний план | вердикт ревью | PR решения (если был) + параметры цикла (бюджет итераций, id этого плана, ссылка на Project).
7. Блокеры, которые может снять только владелец (нет доступа/секрета, необратимое действие, дорогая развилка архитектуры): ОДИН вопрос с твоей рекомендацией и вариантами через task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопрос + рекомендация>). Всё остальное решай сам как архитектор и записывай решение с обоснованием в журнал.

Готово, когда: Список карточек со статусами (из Project) и зависимостями собран, у каждой карточки есть issue в Project (найден готовый или заведён по шаблону), предусловия проверены (или единственный вопрос владельцу задан и отвечен), журнал итераций на эпике существует.

Общее для плейбука «epic-delivery»:

```

```text
Тип шага: next-card — Выбрать одну следующую карточку, у которой закрыты все зависимости, и зафиксировать выбор с причиной — или честно сказать, что карточек не осталось.

1. Номер итерации N: из заголовка ЭТОГО пункта (без суффикса «— итерация N» → N = 1). Id мета-плана (<meta id>) — id задачи этого плана (task_get).
2. Идемпотентность: найди на эпике комментарий с маркером [epic-iter <meta id>#N …]. Если он уже есть (это повторный ран) — ничего не выбирай заново и не публикуй второй: возьми карточку из него, убедись, что её Status в Project — «In progress» (если нет — поставь), и заверши шаг. Сверка: N должен быть = (максимальный N среди комментариев «Итерация …» этого мета-плана) + 1; расхождение — запиши в журнал и бери N из заголовка.

Больше его не редактируй — по этим комментариям считаются итерации. На issue карточки оставь короткий комментарий со ссылкой на комментарий итерации. Обнови строку в журнале итераций (статус «In progress»).
8. Если кандидатов нет, а незакрытые карточки есть (всё заблокировано) — это развилка: реши сам, что разблокировать, или, если это необратимо/дорого, один вопрос владельцу с рекомендацией через task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопрос + рекомендация>); карточкам, ждущим владельца, поставь Status «Blocked» с причиной комментарием в issue.
9. Если незакрытых карточек в Project не осталось (все «Done») — опубликуй «Итерация N: все карточки закрыты» с маркером [epic-iter <meta id>#N card none], а оставшиеся шаги ЭТОЙ итерации (дочерний план, кросс-ревью, обновление плана) пропусти через task_item_skip с этой причиной; шаг «Цикл или финиш» завершит цикл.

Готово, когда: На эпике ровно один комментарий «Итерация N» с маркером [epic-iter <meta id>#N card …]: выбранная карточка со ссылкой на её issue, причиной, видом работы и строками приёмки из task list'а issue, в Project у неё Status «In progress» — или «все карточки закрыты» и шаги итерации пропущены.
```

#### 3. Дочерний инженерный план карточки

```text

Сам работу дочернего плана не делает. task_item_wait перезапускает ВЕСЬ шаг после пробуждения, поэтому шаг всегда начинается с проверки уже запущенного дочернего плана.
