# Плейбук `epic-delivery` — Довести эпик/план архитектуры до конца (мета-цикл)

> Сгенерировано `scripts/build-playbooks.js` из `playbooks-src/epic-delivery.json` и `library/step-types.json`. Правь источники, не этот файл.

**Когда:** Есть эпик и единый план архитектуры с карточками (IMPLEMENTATION-AND-INTEGRATION-PLAN.md) и чек-листом приёмки; нужно автономно, в том числе ночью, пройти карточку за карточкой: дочерний инженерный план с песочницей → независимое кросс-ревью другой семьёй моделей → обновление плана → следующая карточка, и в конце — приёмка по чек-листу.

**Результат:** Все карточки плана доставлены дочерними планами с песочницей и приняты независимым ревью, план архитектуры отражает реальность после каждой итерации, чек-лист приёмки прогнан с отчётом.

- Цикл без конструкции повтора: одна итерация = «Следующая карточка → Дочерний план → Кросс-ревью → Обновление плана → Цикл или финиш»; последний шаг дописывает копию итерации сразу после себя (task_item_add), пока есть карточки и бюджет итераций.
- Карточки строят дочерние планы на OpenCode (их шаги master/bachelor); если OpenCode дважды провалил шаг по качеству — третья попытка на Claude (escalate_to_doctor). Claude (doctor) — только архитектурные шаги мета-цикла: предполётная проверка, выбор карточки, обновление плана, приёмка. Проверяет другая семья моделей (reviewer · doctor → Codex, запасной OpenCode doctor). Кросс-ревью не правит код — только вердикт и замечания.

**Запуск:** `playbook_run(playbook_id: "epic-delivery", goal: "<что делаем>", vars: {epic: "<URL эпик-issue>", arch_repo: "<owner/repo>", max_iterations: 8})` → черновик плана → `task_update(status: "active")`.

## Шаги подробно

### Стадия «Подготовка эпика»

#### 1. Предполётная проверка эпика и журнал итераций

```text
Тип шага: epic-preflight — Перед автономным ночным циклом убедиться, что он вообще может дойти до конца (карточки понятны, мержи и деплой возможны, независимый ревьюер доступен), и завести журнал итераций на эпике — чтобы цикл можно было продолжить после любого сбоя.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Прочитай в репозитории архитектуры документ плана (карточки, их статусы и зависимости), чек-лист приёмки и DECISIONS.md. Выпиши список карточек: id, название, целевой репозиторий (или «новый»), зависимости, текущий статус. Новых документов-планов НЕ заводи — план один.
2. Эпик-issue обязателен и передаётся на входе: открой его (gh issue view). Если его нет или он закрыт — это блокер, эпик не создавай сам.
3. Проверь предусловия цикла для каждого существующего целевого репозитория открытых карточек: есть CI и staging/деплой (без них дочерний план не сможет смержить и проверить), у агента есть доступ на запись. Для карточек «новый репозиторий» — что new-software сможет его завести (права на организацию).
4. Проверь, что независимый ревьюер доступен: шаг кросс-ревью идёт ролью reviewer на уровне doctor, это другая семья моделей (Codex, запасной — OpenCode doctor, не Claude). Если движок Codex сейчас недоступен — отметь это в журнале как риск (ревью уйдёт на запасной движок), это не блокер.
5. Заведи или обнови на эпике ОДИН комментарий «Журнал итераций» (найди существующий по заголовку, не плоди дубли; обновляй через gh api PATCH): таблица карточка | статус | дочерний план | вердикт ревью | PR плана + параметры цикла (бюджет итераций, id этого плана).
6. Блокеры, которые может снять только владелец (нет доступа/секрета, необратимое действие, дорогая развилка архитектуры): ОДИН вопрос с твоей рекомендацией и вариантами через task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопрос + рекомендация>). Всё остальное решай сам как архитектор и записывай решение с обоснованием в журнал.

Готово, когда: Список карточек со статусами и зависимостями собран, предусловия проверены (или единственный вопрос владельцу задан и отвечен), журнал итераций на эпике существует.

Общее для плейбука «epic-delivery»:

```

### Стадия «Итерация: карточка → песочница → кросс-ревью → план»

#### 2. Следующая карточка плана

```text
Тип шага: next-card — Выбрать одну следующую карточку, у которой закрыты все зависимости, и зафиксировать выбор с причиной — или честно сказать, что карточек не осталось.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Номер итерации N: из заголовка ЭТОГО пункта (без суффикса «— итерация N» → N = 1). Id мета-плана (<meta id>) — id задачи этого плана (task_get).
2. Идемпотентность: найди на эпике комментарий с маркером [epic-iter <meta id>#N …]. Если он уже есть (это повторный ран) — ничего не выбирай заново и не публикуй второй: возьми карточку из него и заверши шаг. Сверка: N должен быть = (максимальный N среди комментариев «Итерация …» этого мета-плана) + 1; расхождение — запиши в журнал и бери N из заголовка.
3. Перечитай АКТУАЛЬНЫЕ документ плана (main репозитория архитектуры — прошлая итерация могла его поменять) и журнал итераций на эпике.
4. Кандидаты: карточки не в статусе «сделано», все зависимости которых сделаны; карточка, отклонённая ревью (reject), или новая карточка из блокирующих замечаний — тоже кандидат. Из кандидатов выбери одну: сначала разблокирующие больше всего следующих, потом меньший риск.
5. Определи вид работы: новый репозиторий/сервис → new-software; изменение в существующем → feature; дефект из ревью → debugging. Выпиши строки чек-листа приёмки, которые эта карточка должна закрыть; если карточка вернулась после reject — ссылку на вердикт и его блокирующие замечания.
6. Опубликуй на эпике ОДИН неизменяемый комментарий «Итерация N: карточка <id>» с маркером [epic-iter <meta id>#N card <id>] в первой строке: почему она, вид работы, строки приёмки, блокирующие замечания прошлого ревью (если были). Больше его не редактируй — по этим комментариям считаются итерации. Обнови строку в журнале итераций (статус «в работе»).
7. Если кандидатов нет, а незакрытые карточки есть (всё заблокировано) — это развилка: реши сам, что разблокировать, или, если это необратимо/дорого, один вопрос владельцу с рекомендацией через task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопрос + рекомендация>).
8. Если незакрытых карточек не осталось — опубликуй «Итерация N: все карточки закрыты» с маркером [epic-iter <meta id>#N card none], а оставшиеся шаги ЭТОЙ итерации (дочерний план, кросс-ревью, обновление плана) пропусти через task_item_skip с этой причиной; шаг «Цикл или финиш» завершит цикл.

Готово, когда: На эпике ровно один комментарий «Итерация N» с маркером [epic-iter <meta id>#N card …]: выбранная карточка с причиной, видом работы и строками приёмки — или «все карточки закрыты» и шаги итерации пропущены.
```

#### 3. Дочерний инженерный план карточки

```text
Тип шага: child-plan — Карточку делает отдельный инженерный план с песочницей (new-software / feature / debugging) в фоне; мета-план только запускает его, спит до его конца и записывает исход. Сам работу дочернего плана не делает. task_item_wait перезапускает ВЕСЬ шаг после пробуждения, поэтому шаг всегда начинается с проверки уже запущенного дочернего плана.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Если на эпике для этой итерации записано «все карточки закрыты» — пропусти себя (task_item_skip) с этой причиной.
2. Номер итерации N: из заголовка ЭТОГО пункта (без суффикса «— итерация N» → N = 1). Id мета-плана (<meta id>) — id задачи этого плана (task_get). Карточку итерации возьми из комментария [epic-iter <meta id>#N card <id>] на эпике. Ключ идемпотентности — N + карточка (не карточка одна: после reject следующая итерация запускает НОВЫЙ дочерний план по той же карточке).
3. Найди уже запущенный дочерний план этой итерации: (а) комментарий «Дочерний план итерации N» на эпике с task id; (б) если его нет — task_list и поиск плана, в цели которого есть маркер [epic-iter <meta id>#N card <id>] (id мог потеряться между запуском и записью) — найденный усынови: запиши его task id на эпике, второй НЕ запускай.
4. Если дочерний план найден — task_get(<task id>): статус done / failed / cancelled (терминальный) → прочитай исход (PR и их мерж, итог песочницы и проверки в реальном окружении, последняя ошибка), запиши на эпике и в журнал и заверши шаг, больше не жди. Нетерминальный → проверь дедлайн: 24 ч от времени запуска из комментария; истёк → запиши исход «не уложился в 24 ч» (статус и последний прогресс дочернего плана, сам план не отменяй) и заверши шаг; не истёк → жди (пункт ниже).
5. Если дочернего плана нет — запусти ровно один: playbook_run(playbook_id: <new-software|feature|debugging по выбору итерации>, activate: true, escalate_to_doctor: true, vars: {repo: <owner/name целевого репозитория; для нового — не передавай>}, goal: <первой строкой маркер [epic-iter <meta id>#N card <id>] + название карточки + что сделать + строки чек-листа приёмки дословно + при повторе после reject — блокирующие замечания вердикта дословно со ссылкой + ссылка на эпик + правило «решения принимает архитектор по плану и DECISIONS.md; владельца не спрашивать, кроме необратимых действий и дорогих развилок архитектуры»>). Сразу опубликуй на эпике «Дочерний план итерации N: <task id>, запущен <UTC-время>» и обнови журнал.
6. Жди только нетерминальный дочерний план: task_item_wait(until: {task_done: "<task id дочернего плана>"}, poll_every_sec: 600, timeout_sec: <остаток до 24 ч от запуска>, reason: "ждём дочерний план итерации N") → DURABLE: waiting. После пробуждения шаг начнётся сначала — проверка выше увидит терминальный статус или истёкший дедлайн. Не опрашивай в цикле и не делай работу дочернего плана сам.
7. Провал, отмена или таймаут дочернего плана — не провал этого шага: исход записан, его разберёт кросс-ревью.

Готово, когда: Для итерации N запущен ровно один дочерний план (маркер в цели, task id на эпике), и он в терминальном статусе или истёк 24-часовой дедлайн; исход с PR и доказательствами записан на эпике.
```

#### 4. Независимое кросс-ревью (другая семья моделей)

```text
Тип шага: cross-review — Строит OpenCode (при провале — Claude), архитектуру ведёт Claude — Codex проверяет «с другой стороны». Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Если на эпике для этой итерации записано «все карточки закрыты» — пропусти себя (task_item_skip) с этой причиной.

Маркер ревью: [epic-review <meta id>#N child <child task id> sha <sha1,sha2…>] (sha none, если ничего не смержено).
3. Если на эпике уже есть ИТОГОВЫЙ вердикт с этим маркером (N + child) — повторный ран: второй не публикуй, заверши шаг. Если есть частичные комментарии с этим маркером — это продолжение: не повторяй уже проверенное, продолжай с оставшегося.
4. Собери, что поставил дочерний план: его task (task_get), смерженные PR и их диффы (gh pr diff), команду песочницы и её вывод, доказательства проверки в реальном окружении (логи, URL, ответы), issue дочернего плана.
5. Сверь с: критериями карточки в документе плана, строками чек-листа приёмки для этой карточки, инвариантами INV-* и решениями DECISIONS.md репозитория архитектуры. Проверяй по доказательствам, а не по словам итога: запусти песочницу/тесты сам, если это возможно без записи в прод.
6. Вынеси вердикт: accept / accept-with-followups / reject. Замечания пронумеруй; у каждого — блокирующее или нет, где (файл/PR/строка), почему, что сделать. Проваленный, отменённый или не уложившийся в дедлайн дочерний план — reject с причиной.
7. Опубликуй ревью ОДНИМ комментарием на эпике: первой строкой маркер [epic-review <meta id>#N child <child task id> sha <…>], затем «Кросс-ревью итерации N, карточка <id>: <вердикт>» и строка «Ревьюер: <движок/модель, которые реально выполнили этот шаг>». Ссылку — в журнал итераций.
8. Ревью ограничено по времени (~40 мин на ран). Если не успеваешь проверить всё к ~30-й минуте: опубликуй ЧАСТИЧНЫЕ замечания комментарием с тем же маркером и пометкой «частичное — вердикта нет» (что проверено, что осталось) и добавь продолжение сразу после себя: task_item_add(after_item_id = id ЭТОГО пункта) с тем же контрактом (executor_role, minimum_model_level, context_budget, validation, instructions, stage) и заголовком « — продолжение». На частичной проверке НИКОГДА не ставь accept.
9. Блокирующие замечания заведи issues в целевых репозиториях (ссылка на ревью и карточку) — шаг обновления плана превратит их в карточки. Код сам не правь и PR не открывай.

Готово, когда: На эпике опубликован итоговый вердикт с маркером [epic-review <meta id>#N child <task id> sha <…>] и именем движка-ревьюера, с пронумерованными замечаниями (блокирующее/нет), ссылка в журнале — или опубликовано частичное ревью с тем же маркером и сразу после шага добавлено продолжение.
```

#### 5. Обновление плана архитектуры по итогам ревью

```text
Тип шага: architecture-update — Архитектор применяет ревью к единственному плану: статус карточки, следующие шаги, отметки приёмки и изменившиеся решения — через PR с CI и мержем, чтобы следующая итерация выбирала по актуальному плану.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Если вместо значения тут имя в фигурных скобках — его не передали, бери значение по умолчанию: trained-assist/trained-agent-architecture, IMPLEMENTATION-AND-INTEGRATION-PLAN.md, ACCEPTANCE-CHECKLIST.md, 8. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Если на эпике для этой итерации записано «все карточки закрыты» — пропусти себя (task_item_skip) с этой причиной.
2. Номер итерации N: из заголовка ЭТОГО пункта (без суффикса «— итерация N» → N = 1). Id мета-плана (<meta id>) — id задачи этого плана (task_get). Дочерний план итерации — из комментария «Дочерний план итерации N».
3. Привязка к вердикту: найди на эпике ИТОГОВЫЙ вердикт кросс-ревью с маркером [epic-review <meta id>#N child <тот же child task id> …] (не частичный). Нет такого — статусы карточек НЕ меняй: заверши шаг ошибкой (task_item_exception, причина «нет итогового вердикта итерации N для child <id>»). Вердикт прошлой итерации или другого дочернего плана не используй никогда.
4. Реши как архитектор по этому вердикту: accept → карточка «сделано»; accept-with-followups → «сделано» + follow-up карточки; reject → карточка обратно в работу с блокирующими замечаниями как критериями (или новые карточки на них).
5. Обнови ТОЛЬКО существующий документ плана: статус карточки, ссылки на PR/вердикт, следующие шаги и зависимости, которые ревью поменяло. Новых документов-планов не создавай.
6. В чек-листе приёмки отметь строки, закрытые с доказательством (ссылка на PR/лог/вердикт); строки без доказательства не отмечай.
7. Если решение поменялось — допиши запись в DECISIONS.md (что, почему, ссылка на вердикт). Дорогую или необратимую развилку — один вопрос владельцу с рекомендацией через task_item_wait(awaiting_user: true, timeout_sec: 259200, reason: <вопрос + рекомендация>); остальное решай сам.
8. Идемпотентность PR: в теле PR первой строкой маркер [epic-plan <meta id>#N]; перед открытием поищи открытый/смерженный PR с этим маркером (gh pr list --search) и продолжай его, второй не открывай. Ветка → PR в репозиторий архитектуры → дождись CI → смержи (gh pr merge --squash; пока CI идёт — task_item_wait(until: {ci_green: "<PR url>"}, poll_every_sec: 300, timeout_sec: 7200, reason: "ждём CI плана"), а не опрос в цикле). В итоге шага — URL PR.
9. Обнови журнал итераций на эпике: статус карточки, вердикт, PR плана.

Готово, когда: Статус карточки изменён по итоговому вердикту именно этой итерации и этого дочернего плана; PR с маркером [epic-plan <meta id>#N] смержен; журнал итераций отражает новый статус.
```

#### 6. Цикл или финиш

```text
Тип шага: loop-or-finish — Повторов в плане нет — цикл делается легальной самоправкой: пока карточки есть и бюджет итераций не исчерпан, шаг дописывает в этот же план следующую итерацию сразу после себя.

Эпик: {epic}. Репозиторий архитектуры: {arch_repo}; документ плана: {plan_doc}; чек-лист приёмки: {acceptance_doc}; бюджет итераций: {max_iterations}. Ты — архитектор: решения принимаешь сам по плану и DECISIONS.md и записываешь их с рекомендацией/обоснованием; владельца не спрашивай, кроме необратимых действий и дорогих развилок архитектуры. План один — новых документов-планов не заводи.

Чек-лист (пройди все пункты за этот ран; в ИТОГЕ ШАГА коротко отметь каждый: ✅ сделано / ⏭ не нужно — почему):
1. Номер итерации N: из заголовка ЭТОГО пункта (без суффикса «— итерация N» → N = 1). Id мета-плана (<meta id>) — id задачи этого плана (task_get). Сверка: число комментариев «Итерация …» с маркером [epic-iter <meta id>#…] на эпике должно быть N; бюджет итераций — из строки контекста.
2. Есть ли незакрытые карточки в актуальном плане (main репозитория архитектуры) и не записано ли «Итерация N: все карточки закрыты»?
3. Если карточки есть и N < бюджета: следующая итерация N+1 = 5 пунктов по порядку — «Следующая карточка плана», «Дочерний инженерный план карточки», «Независимое кросс-ревью (другая семья моделей)», «Обновление плана архитектуры по итогам ревью», «Цикл или финиш», каждый с заголовком <базовый заголовок без старого суффикса> + « — итерация N+1».

Контракт копируй из пунктов итерации N без изменений (пункты « — продолжение» не копируй): stage, execution_kind, executor_role, minimum_model_level, context_budget, validation, instructions.
5. Проверь через task_get: ровно 5 пунктов « — итерация N+1» стоят сразу после этого шага, в правильном порядке и перед финальной приёмкой; дубли — task_item_skip с причиной «дубль».
6. Иначе — финиш: причина (все карточки закрыты / исчерпан бюджет итераций — тогда список оставшихся карточек). Ничего не добавляй; дальше пойдёт финальная приёмка.
7. Запиши решение (итерация N+1 добавлена / финиш и почему) комментарием на эпике и в журнал.

Готово, когда: Ровно 5 пунктов итерации N+1 стоят сразу после этого шага в правильном порядке с теми же контрактами — или записан финиш с причиной.
```
