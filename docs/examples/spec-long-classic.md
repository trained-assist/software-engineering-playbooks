# ТЗ: учёт заявок на ремонт для сети автосервисов (long)

Статус: образец нового стиля (oldschool). Контекст — `scripts/sandbox/fixtures/context/`.

## 1. Цель

Система должна принять заявку на ремонт из веб-формы и из мобильного кабинета мастера, назначить её филиалу и показывать диспетчеру общую очередь в реальном времени. Сейчас заявка живёт в почте и в чате мастера, единого учёта нет.

## 2. Область и ограничения

- Три филиала, у каждого свой диспетчер; аккаунты мастеров и диспетчеров уже есть в Active Directory заказчика — новые логины не заводим.
- Пиковая нагрузка — до 300 заявок в час, круглосуточно.
- Персональные данные клиентов хранятся только на серверах в РФ (152-ФЗ).
- SMS-уведомления на первом этапе не требуются.

## 3. Требования к системе

- Система должна принимать заявку из веб-формы и из мобильного кабинета мастера.
- Система должна назначать заявке филиал и хранить историю смены статусов.
- Система должна отправлять уведомление диспетчеру при появлении новой заявки.
- Система должна авторизовывать сотрудников через существующий Active Directory по LDAP.
- Система должна показывать диспетчеру очередь заявок в реальном времени.
- Система должна сохранять работоспособность при пиковой нагрузке до 300 заявок в час.

## 4. Инфраструктура

Поднимается следующий стек (Docker Compose, контур заказчика в РФ, наружу только исходящие соединения):

| Компонент | Что это | Назначение |
|---|---|---|
| api | Node.js 20, HTTP/REST, порт 8080 | приём заявок, авторизация, отдача очереди |
| web | SPA (nginx, порт 8081) | кабинет диспетчера |
| pwa | статика, порт 8082 | кабинет мастера |
| postgres | PostgreSQL 16, порт 5432 | заявки, история статусов, пользователи |
| redis | Redis 7, порт 6379 | очередь уведомлений + канал публикации |
| worker | Node.js 20 | читает очередь Redis, шлёт уведомления |
| ldap-connector | Node.js 20 | связь с AD заказчика |

Тестовое окружение — тот же docker-compose на машине разработчика: `localhost:8080` (api), `localhost:8081` (web), `localhost:5432` (postgres), `localhost:6379` (redis). Фикстуры: 3 филиала, 10 мастеров, 3 диспетчера, 50 заявок с разными статусами.

## 5. Взаимодействие частей

- Браузер диспетчера → api: HTTP/REST `POST /api/requests`, `GET /api/queue`.
- api → postgres: SQL-запросы через пул соединений, транзакция на создание заявки.
- api → redis: `LPUSH requests.new` — сообщение с id заявки, филиалом и временем.
- worker ← redis: `BLPOP requests.new`; далее worker → api (HTTP, внутренний порт 8080) на запись события уведомления, затем `PUBLISH events.<dispatcherId>`.
- api → браузер: WebSocket `/ws` подписывается на `events.*`, очередь обновляется без перезагрузки.
- api/worker → ldap-connector → AD заказчика: LDAP bind по логину/паролю сотрудника, без локальных паролей.
- Кто инициирует: заявку заводит мастер или диспетчер, уведомление — воркер, отрисовку — WebSocket-канал.

## 6. Этапы

1. Схема postgres, миграции, seed фикстур.
2. api: авторизация LDAP, CRUD заявки, очередь.
3. worker + Redis: уведомления диспетчеру.
4. web: очередь в реальном времени, смена статуса.
5. pwa: создание заявки мастером.
6. Нагрузочный прогон 300 заявок в час.

## 7. Как запускается и как проверяется

Команды поднятия окружения:

```
docker compose up -d postgres redis
npm ci
npm run migrate
npm run seed            # фикстуры: филиалы, мастера, диспетчеры, заявки
npm run dev             # api на localhost:8080, worker, web на localhost:8081
```

Данные для входа: `dispatcher1 / …` из seed, AD не обязателен — локальный LDAP-стенд поднимается скриптом `npm run ldap:stand` (порт 1389).

Наблюдаемый сигнал замкнутой петли: после `curl -X POST localhost:8080/api/requests …` в консоли worker появляется строка `notified dispatcher1`, а в браузере диспетчера заявка появляется в очереди без перезагрузки (WebSocket `events.dispatcher1`).

Уровень автономности: S0 — нет исполнения; S1 — статический анализ; S2 — код запускается частично; S3 — автотесты с моками; S4 — стейджинг с реальными зависимостями; S5 — полный замкнутый цикл без человека. План доводит проверку до S5 на локальном docker-compose: автотесты api/worker и смоук `npm run smoke`, который поднимает стенд, создаёт заявку, ждёт уведомление и проверяет очередь. Граница, за которой нужен человек: приёмка UI диспетчером и подпись по 152-ФЗ.

## 8. Критерии приёмки

- Заявка, созданная в pwa, видна в очереди web не пиком чем через 2 с.
- Уведомление диспетчера приходит при появлении заявки (событие в очереди Redis обработано воркером).
- Вход по AD работает для учётной записи из seed.
- Прогон 300 заявок в час проходит без ошибок в логах api и worker.
- Все персональные данные хранятся в postgres в контуре РФ.
