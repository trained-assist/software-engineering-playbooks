# Как проверять, что шаг плана действительно выполнен, без присмотра за агентами

Исследование, 2026-09-27. Повод — первый e2e плейбука `new-software` на проде (план `2548635a`, профиль `playbooks-e2e`).

Цель: такой уровень контрактов шагов, при котором **бесплатные модели справляются**, а ложное «готово» ловится машиной, а не человеком.

---

## 1. Что увидели в e2e

Первые 4 шага (`define-use-case`, `infra-discovery`, `explore-context`, `requirements-complexity`) отработали на `opencode/free` за 1–2 минуты каждый. Каждый закончил итогом вида «✅ сценарий записан в `docs/user-scenarios/todo-cli.md`» и был засчитан как `done`.

На деле:

| Факт | Что это значит |
|---|---|
| Файл создан, но лежит **незакоммиченным** в отдельном worktree этого шага | Для следующих шагов артефакта нет (каждый шаг заводил свой workspace — фикс trained-assist-agent#1640) |
| LLM-судья по всем 4 шагам вынес `fail` или `inconclusive`: «результат шага не представлен» | Судья смотрел в workspace профиля, а не туда, где агент работал. Проверять ему было нечего |
| Несмотря на это, все 4 шага — `done` | **Вердикт проверки записывается, но шаг не блокирует.** Гейт срабатывает только на финализации всего плана (P3d-2) |
| Проверки шагов — смысловые ключи (`use_case_value_and_steps_written: true`) | Детерминированно проверить нечего, остаётся LLM-судья по тексту ответа агента |

Итог: **агент утверждает, судья не видит, шаг всё равно проходит.** Ошибка всплывёт только в конце плана, а каждый следующий шаг строится на непроверенном.

## 2. Корень проблемы

Шаг сейчас отвечает **текстом**, а проверяется **смыслом** этого текста. У шага нет машиночитаемого результата — «что именно я произвёл и где это лежит». Отсюда три следствия:

1. Нечего проверить детерминированно: судье приходится верить словам.
2. Следующий шаг получает пересказ («ИТОГ ШАГА»), а не ссылку на артефакт.
3. Проверка без блокировки: плохой шаг не останавливает план.

Почти любой шаг инженерного процесса на самом деле заканчивается чем-то **проверяемым по контракту**: коммит в ветке, файл на этом коммите, issue, PR, зелёный CI, merge, живой `/health`, команда с exit 0. Смысловыми по-настоящему являются только качество текста и решений (хороший ли сценарий, разумен ли дизайн).

---

## 3. Варианты решения

### A. Типизированный результат шага (step outputs) — главное

Каждый тип шага в `library/step-types.json` объявляет **схему результата**. Агент заканчивает ответ блоком:

```
STEP_OUTPUT {"branch":"eng/playbooks-e2e-plan-2548635a","commit":"3f2a9c1","scenario_path":"docs/user-scenarios/todo-cli.md"}
```

Исполнитель:
1. Парсит блок и валидирует по JSON Schema типа шага. Нет блока или не та схема → шаг не засчитан, агенту уходит конкретная ошибка.
2. **Детерминированно проверяет артефакты** по типам полей:
   - `commit` + `branch` → коммит есть в ветке на remote (`git ls-remote` / GitHub API);
   - `*_path` + `commit` → файл есть на этом коммите (`git cat-file -e <sha>:<path>` / Contents API);
   - `issue_url`, `pr_url` → существуют (GitHub API);
   - `command` → exit 0 в workspace плана.
3. Сохраняет результат в `task_items.evidence_json.outputs`. **Следующие шаги получают его как типизированный вход** (`{{steps.define-use-case.scenario_path}}`), а не пересказ.

Это прямо ваш вопрос «может шаг принимать атрибуты JSON»: да, и на входе, и на выходе.

Примеры контрактов:

| Тип шага | Результат (outputs) | Проверка без модели |
|---|---|---|
| `define-use-case` | `branch`, `commit`, `scenario_path` | файл на коммите в ветке |
| `infra-discovery` | `branch`, `commit`, `inventory_path` | то же |
| `requirements-complexity` | `flags` (список `{req, flag, source}`), `commit`, `path` | схема + файл; есть ли 🔴/⚫ — поле, от него зависит уровень следующего шага |
| `plan-declaration` | `issue_url` | issue существует |
| `sandbox` | `command`, `commit`, `expected: "fail"` | команда падает на этом коммите |
| `implement` | `commit`, `command` | команда проходит на этом коммите |
| `verify-local` | `commands` | все exit 0 |
| `open-pr` | `pr_url` | PR существует и указывает на ветку плана |
| `deployed` | `health_url`, `commit` | `/health` содержит commit |

**Бонус для бесплатных моделей:** заполнить JSON по схеме они умеют хорошо (бенч `json` и `tool` проходят почти все модели лестницы `free`). Размытую задачу «напиши итог» — хуже. Жёсткий контракт выхода — это **подсказка**, а не только проверка.

### B. Maker–checker: второй агент проверяет DoD

Там, где проверить можно только смысл (качество сценария, дизайна, ревью), — пара: **исполнитель** делает шаг, **проверяющий** получает DoD шага (подшаги из библиотеки = чек-лист) и **сам артефакт по ссылке из outputs** (не пересказ!), и выносит `pass` / `fail` с причинами по каждому пункту.

- Проверяющий — **другая модель**, чем исполнитель. Это как раз задача для двух разных бесплатных профилей (`free-a` исполняет, `free-b` проверяет). Ошибки у разных моделей коррелируют слабее.
- Один дешёвый вызов на шаг, только для смысловых шагов.
- `fail` → шаг возвращается исполнителю с замечаниями проверяющего (одна итерация), дальше эскалация уровня.
- Индустрия: four-eyes principle, maker-checker в финансах, «LLM-as-judge» с рубрикой; важно, что судья видит **артефакт**, а не самоотчёт.

Уже есть частично: `validation_mode: programmatic+llm` (LLM-судья). Не хватает двух вещей: судья должен получать **артефакт по outputs**, и его вердикт должен **блокировать шаг**.

### C. Планировщик задаёт измеримые подшаги

Шаг `propose-change` пишет Tasks-чек-лист. Сейчас это текст, и `implement` идёт по нему «на честном слове». Вместо этого propose выдаёт в outputs список слайсов, **у каждого — команда проверки**:

```json
{"slices":[{"title":"todo add","verify":"node --test test/add.test.js"},
           {"title":"todo list","verify":"node --test test/list.test.js"}]}
```

Исполнитель разворачивает их в **дочерние durable-шаги** с программной проверкой `command_exit_zero`. Планирование делает сильная модель один раз, а бесплатная исполняет мелкие шаги с машинной приёмкой. Это прямой ответ на «на старте или на шаге крупнее планировщик задаёт измеримые шаги».

Нужно в рантайме: шаг может **добавить шаги в свой план** с контрактом (сейчас `task_item_add` принимает только старые поля).

### D. Кастомный системный промпт для бесплатных моделей

Короткий, жёсткий промпт-«протокол» для уровня `free`: «сначала прочитай контракт outputs → сделай → закоммить → проверь сам командой из контракта → выдай STEP_OUTPUT». Это помогает, но **сам по себе не решает**: промпт — просьба, а контракт — проверка. Это дополнение к A, а не замена.

---

## 4. Рекомендация

**A + блокирующая проверка — обязательно и первым. B — для смысловых шагов. C — следующим этапом. D — дёшево, попутно.**

1. **Проверка шага блокирует шаг, а не только финализацию.** `fail` → шаг не `done`, возврат с конкретной причиной. `inconclusive` на детерминированной проверке → тоже не `done`.
2. **`outputs`-схема для каждого типа шага** в библиотеке + блок `STEP_OUTPUT` + детерминированные проверки артефактов по типам полей (коммит/файл/issue/PR/команда/URL).
3. **Outputs → входы следующих шагов** вместо пересказа (пересказ «ИТОГ ШАГА» оставить как человекочитаемое дополнение).
4. **Maker–checker** для `define-use-case`, `requirements-complexity`, `propose-change`, `review`: проверяющий на другой модели получает DoD-чек-лист и артефакт по ссылке.
5. **Измеримые слайсы от планировщика** → дочерние шаги с `command_exit_zero`.

Почему не «сторожить»: всё это работает без человека. Человек нужен, только когда шаг честно не может пройти контракт (тогда это `awaiting_user` с конкретным вопросом, механизм уже есть).

## 5. Что менять и где

| Что | Где |
|---|---|
| Блокирующая проверка агентского шага | trained-assist-agent: `src/gtd-controller.js` (ветка ответа `DURABLE: done` — сейчас пишет вердикт и всё равно `completeItem`) |
| Парсинг `STEP_OUTPUT` + валидация по схеме + хранение в evidence | trained-assist-agent: `gtd-controller.js`, `src/playbook-validators.js` (новые валидаторы `artifact_committed`, `file_at_commit`, `issue_exists`, `pr_exists`) |
| `outputs` в контракте шага | software-engineering-playbooks: `library/step-types.json` + сборка; trained-assist-agent: `contracts/playbook.schema.json` (поле `outputs` у шага), компилятор |
| Outputs → входы следующих шагов | `gtd-controller.js`: блок «ВХОДЫ ОТ ПРОШЛЫХ ШАГОВ» в промпте из `evidence_json.outputs` |
| LLM-судья видит артефакт, а не workspace профиля | `playbook-validators.js`: `collectDocExcerpts` читать из workspace плана / файла по outputs |
| Maker–checker | новый режим проверки `validation_mode: checker` + профиль проверяющего в `level_map` |
| Дочерние шаги от планировщика | `task_item_add` с контрактом (`execution_kind`, `validation`, `wait`) |

## 6. Как проверить, что стало лучше

Тот же e2e (`scripts/e2e/playbooks-e2e.js`) — метрики на план:
- доля шагов, засчитанных без проверенного артефакта → **0**;
- сколько раз шаг вернулся исполнителю по контракту и прошёл со второй попытки (показатель, что бесплатная модель справляется с подсказкой);
- доля шагов, дошедших до эскалации на `doctor`;
- план доходит до финализации без ручного вмешательства.
