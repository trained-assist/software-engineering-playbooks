# Перенос генерации ТЗ в инженерный репозиторий — требования и флаги сложности

Стадия: frame (требования). Источник: бриф владельца (Директивы 2.В и 3, голос 28.09.2026),
исходный код `trained-assist-freelance-skill` → `src/mcp-skills/tools/10-freelance-project.js`
(`SPEC_VOICE_RULES`, `buildSpecInstruction()`), параллельный план движка сложности.

Цель: генерация ТЗ (long/short) переезжает в `trained-assist-engineering`; содержание
получает инженерную конкретику и sandbox-блок, стиль становится отдельным переключателем.
Спецификация использует расчёт сложности ВТОРИЧНО и живёт с ним в одном репо.

## Флаги сложности требований

Масштаб: ⚪ прозрачный · 🟢 аддитивно/локально · 🟡 задевает общий контракт/интеграцию ·
🔴 доступ/деньги/необратимая миграция · ⚫ неоднозначность. **🔴 и ⚫ отсутствуют** (см. ниже).

## Челлендж тяжёлых пунктов (🟡)

- **R1 / R7 / R15 (контракт и границы переезда).** Цена: меняются имена MCP-тулов и путь записи ТЗ;
  возможны ссылки на старые имена в промптах/каталоге. Дешёвая альтернатива: сохранить прежние
  идентификаторы тулов при переезде — НО это противоречит требованию «именовать по конвенции
  engineering-репо» и оставит кросс-репо путаницу, которую владелец как раз хочет убрать.
  Решение: имена по конвенции engineering + после мержа проверить, что в freelance не осталось
  ссылок на удалённое (шаг R15), и синхронизировать каталог. Обратимо через revert.
- **R13 (гейт CI/staging).** Не блокер работы: стандартный контракт доставки, снимается зелёным прогоном.
- **R4 (каталог).** Реальное ограничение, но точные имена артефактов в брифе устарели — см. ниже.

## Открытый вопрос по артефактам каталога (не блокер, решается на design/реализации)

Бриф ссылается на `config/skill-catalog.json` (секция engineering), контракт `test/skills-resolve.test.cjs`
и `docs/how-to-move-a-tool-to-a-domain-repo.md` в `trained-assist-agent`. Проверено на диске 28.09:
по этим именам файлов НЕТ. Актуальный механизм в agent-репо описан в `docs/how-to-add-skill.md`
(каталог — `SKILLS` в `src/mcp-skills/tools/00-meta.js`; **без** массива `tools[]`) и
`docs/domain-skill-repo-test-rules.md` (правила тестов domain-репо). Требование R4 сохраняется
(каталог должен знать новый модуль), но привязку к конкретным устаревшим путям надо уточнить по факту
на design-шаге. Это расхождение имён — не ⚫: поведение однозначно, меняется только адрес правки.

## Почему нет 🔴 и ⚫

- Нет модели доступа/прав, безопасности, биллинга, необратимой миграции данных, мульти-тенантности → 🔴 не применим.
- Нет противоречивых пересекающихся сценариев с разным неопределённым поведением: спорные места
  (где живёт параметр стиля, имена/путь новых тулов, третий вариант документа) разрешаются штатно
  на шаге design, а не требуют решения владельца. Владелец явно запретил задавать вопросы по этой
  задаче (направление согласовано голосом 28.09.2026) → ухода в ожидание (awaiting_user) нет.

## Минимальный набор и принятые решения

1. Новый модуль-генератор ТЗ в engineering-репо: содержание — конкретика (R5) + sandbox-блок (R6)
   в правилах для long и short (R8); стиль — отдельный переключаемый параметр, default = новый (R7);
   третий вариант по умолчанию не заводим (R9).
2. Переезд = новый файл-сосед (R2) + `package.json scripts.check` (R3) + каталог (R4, адрес уточнить)
   + point-of-integration в docs с движком сложности без его дублирования (R10, R17).
3. Проверка: детерминированный тест сборки инструкции (R11), локальные `npm test`/`npm run check`,
   CI/staging (R13), смоук-образец ТЗ на диск (R14), e2e или зафиксированный скип (R12).
4. После мержа — отдельный PR по выносу спецификации из freelance с явными границами (R15).
5. Не в этот PR, только метка в docs: этап 2 и сейлз-форма (R16).
