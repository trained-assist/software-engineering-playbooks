# Инженерные плейбуки: методология sandbox-first

Три плейбука, по которым агент ведёт разработку от запроса до проверки вживую:

| Плейбук | Когда | Файл | Шагов |
|---|---|---|---|
| `feature` | Фича или изменение в существующем продукте. Самый частый случай, дефолт | `playbooks/feature.json` | 15 |
| `debugging` | Баг: что-то работало и сломалось, или ведёт себя не так, как описано в user story | `playbooks/debugging.json` | 16 |
| `new-software` | Новый сервис или модуль с нуля, архитектура свободна | `playbooks/new-software.json` | 19 |

Плейбук — это шаблон. `playbook_run` компилирует его в durable-план, то есть экземпляр. Каждый шаг плана выполняется отдельно, разными моделями по контракту шага, и переживает рестарты. Runtime для этого живёт в `trained-assist-agent`: `playbook_run`, `runDueDurable`, валидаторы. Здесь хранится только содержание.

---

## 1. Подход: sandbox-first (execution-driven development)

**Тезис.** Спецификации (SDD, OpenSpec, user stories, Agile) давно известны. Для агентной разработки главный рычаг другой: **скорость агента равна скорости его цикла «изменил → увидел результат»**. Машина на порядки быстрее человека, но только пока ей не надо ждать человека. Поэтому сначала вкладываемся в среду, где агент сам, без человека, воспроизводит сценарий. Код пишем потом.

Коротко: **сначала замкнуть цикл обратной связи, потом писать код.**

Как это соотносится с индустриальными практиками:

| Практика | Что берём | Чем sandbox-first отличается |
|---|---|---|
| Spec-driven development / [OpenSpec](https://openspec.dev) (explore → propose → apply → archive) | Типизированные шаги, дельта-спеки, архив в источник истины | OpenSpec отвечает на вопрос «что строить». Мы добавляем «как агент сам проверит, что построил»: песочница стоит отдельным шагом до кода |
| TDD / BDD (Given/When/Then) | Приёмка из шагов user story; сначала красный тест | Красным должен быть весь пользовательский сценарий в песочнице, а не только юнит |
| Inner loop / outer loop (DevEx), hermetic tests (Google) | Быстрый локальный цикл, герметичность | Цель — S5: цикл полностью без человека |
| DORA (lead time, change failure rate) | Маленькие PR, быстрый CI, проверка деплоя | Деплой и CI проверяются пробами без модели, агент ждёт их, не тратя токены |
| Shape Up (appetite, rabbit holes, no-gos) | Челлендж сложных требований до работы | Флаги сложности 🟢🟡🔴⚫ |
| ADR / design docs, lab notebook | «Бумаги учёного» | GitHub issue плюс журнал запуска: по ним другой агент или человек доводит работу |
| SRE postmortem | Первопричина, защита на будущее | Шаг `archive` в `debugging` делает мини-постмортем |

OpenSpec как инструмент напрямую не ставим. Берём его типизацию стадий: explore / propose / apply / archive встречаются как `step_type` в наших плейбуках.

## 2. Шаблон → экземпляр → журнал. Насколько детализировать

- **Стадия** — крупная фаза (frame, explore, propose, sandbox, apply, deliver). Стабильна между плейбуками.
- **Шаг** (durable item) — единица, у которой есть **своя проверка** и свой исполнитель. Каждый шаг — отдельный запуск агента или программная проверка без модели. Шаг делаем тем мельче, чем ценнее отдельная проверка.
- **Подшаги** — нумерованный чек-лист внутри `instructions`. Агент проходит их «чик-чик-чик» за один запуск. Именно здесь детализация дешёвая: 3–7 подшагов на шаг — нормально.
- **Экземпляр**: шаг `propose` пишет в журнал конкретный чек-лист слайсов (Tasks), а `implement` идёт по нему. Шаблон остаётся общим, экземпляр становится детальным.

Правило детализации: **новый durable-шаг заводим, только если у него своя проверка, своя модель или своё ожидание.** Всё остальное — подшаги.

**Журнал запуска** (run notebook, `~/users/<профиль>/playbook-runs/<taskId>.md`) — лабораторный журнал плана. Каждый шаг выполняет новый процесс без памяти, поэтому шаг обязан прочитать журнал до работы и дописать свой раздел после. В журнале лежат intake, решения, ссылки на issue и PR, объявленные пробы. GitHub issue дублирует главное наружу.

## 3. Лестницы и флаги

### Ценность (V) — насколько доказано, что это нужно
V5 — за это уже платят, или есть запрос платящего клиента · V4 — много пользователей, CustDev или поисковый спрос · V3 — отзывы, фича-реквесты · V2 — оценка sales или маркетолога (норм для средней фичи) · V1 — оценка инженера (норм для мелкой) · V0 — не указано.

Зачем лестница: если уровень низкий для масштаба задачи, агент **явно** говорит юзеру о риске, что задачу поймут неправильно, и юзер может дополнить. Сначала агент ищет историю в репозитории и не пытает юзера анкетой.

### Обратная связь (S) и воспроизведение бага (L) — одна лестница
| Уровень | Разработка (S) | Баг (L) |
|---|---|---|
| 5 | Замкнутая песочница: агент сам прогоняет сценарий end-to-end | Повторяется по требованию (тест, staging) |
| 4 | Эффект виден в реальной среде (логи, метрики), вызвать сам не может | Видна в логах, вызвать не можем |
| 3 | Есть чёткие шаги, прогон требует человека | Чёткий репорт шагов от юзера |
| 2 | Есть конкретный сигнал без среды (контракт, текст ошибки) | Недефолтный текст ошибки или exception |
| 1 | Есть факт с привязкой ко времени и модулю | То же |
| 0 | Только со слов | Со слов |

Уровень — это одновременно и оценка сложности для юзера. S5 значит «выглядит несложно, делаю»; S3 и ниже — предупреждаем о стоимости.

### Доступы (A) — что просить у юзера (`new-software`)
A0 ничего (всё локально) · A1 тестовые или sandbox-ключи · A2 отдельный staging с полными правами · A3 чтение прод-логов и метрик · A4 деплой в прод. Для каждого уровня агент называет, какой S-уровень он откроет.

### Флаги сложности требований
- 🟢 **green** — не меняет модель системы (текст, цвет, поле в ответе).
- 🟡 **yellow** — новая сущность, интеграция, платформа или миграция.
- 🔴 **red** — права доступа, роли, группы пользователей, мультитенантность, деньги, безопасность, необратимые данные. Плодят состояния по всей системе, поэтому **обязательно челленджим** — и для себя, и с юзером.
- ⚫ **black** — неоднозначность: пересекающиеся или противоречивые сценарии. Строить нельзя, пока не разрешено.

Отдельное правило: «уже так написано в коде» — не требование. Если существующий код сложнее задачи, меняем код, а не тащим его сложность в план.

## 4. Библиотека типов шагов

`step_type` у каждого шага берётся из `library/step-library.json`. Тест проверяет, что тип известен и контракт шага (agent/programmatic, роль, ожидание) совпадает с библиотекой.

| Тип | Кто | Суть |
|---|---|---|
| `intake` / `intake-bug` | researcher | User story: ценность, V, шаги, Given/When/Then · для бага: симптом, ожидание, L |
| `environment` | researcher | Инвентаризация среды и меню доступов A0–A4 |
| `explore` | researcher | Сначала внутри репо, потом снаружи |
| `feedback-level` | researcher | Текущий и целевой S, что нужно для S5 |
| `complexity-review` | reviewer | Флаги 🟢🟡🔴⚫, челлендж 🔴, стоп на ⚫ |
| `approaches` | developer | Ранжирование подходов по достижимому S |
| `spike` | developer | Проверка самого рискованного допущения, возможен откат к подходам |
| `propose` | developer | Proposal + design + Tasks (слайсы) |
| `declare-plan` | developer | GitHub issue + объявление проб |
| `sandbox` | developer | Песочница: сценарий гоняется без человека, сейчас красный |
| `reproduce` / `root-cause` | developer / researcher | Поднять L до максимума; первопричина |
| `implement` | developer | Слайсы до зелёного; своя ветка и workspace |
| `verify-local` / `verify-sandbox` | без модели | Гейт по пробе `tests` / `scenario_e2e` |
| `open-pr` | developer | PR, полный URL в журнал |
| `wait-ci` / `wait-merge` / `wait-deploy` | без модели, ожидание | CI зелёный / смёржено / деплой жив |
| `wait-capture` / `wait-error-gone` | без модели, ожидание | Ошибка снова появилась / ушла из логов |
| `sandbox-to-real` | developer | Перенос в реальную среду, health с commit |
| `verify-live` | verifier | Шаги user story в реальной среде, с evidence |
| `archive` | researcher (дешёвая модель) | User stories и requirements-log, закрыть issue, сжать журнал |

## 5. Ожидания: процесс засыпает и просыпается

Программный шаг с `"wait": {"poll_sec": N, "timeout_sec": M}` не падает, пока условие не выполнено:
- засыпает со статусом `waiting` и опрашивается раз в `poll_sec` (тик исполнителя — 5 минут) **без модели**;
- попытку не тратит и переживает рестарт, потому что всё хранится в SQLite;
- по таймауту план останавливается, владелец получает уведомление (`task_failed`).

На ожидающем шаге LLM-судья не вызывается, иначе он мог бы «засчитать» событие, которое ещё не наступило.

| Чего ждём | Валидатор |
|---|---|
| CI зелёный / PR смёржен | `ci_green` / `merged` (PR берётся из журнала) |
| Деплой прошёл | `probe: deploy_live` → `http_ok <url>/health contains <sha>` |
| Ошибка ушла из логов / появилась снова | `probe: error_gone` / `probe: error_captured` → `command …` |
| Юзер дал креды (хоть через 3 дня) | `token_present: "<service>"` |
| Другой план завершён | `task_done: "<taskId>"` |
| Что угодно ещё | `probe` с `command` |

**Пробы.** Шаблон не знает URL деплоя или команду для логов конкретного запуска. Поэтому шаг `declare-plan` объявляет пробы в журнале:

```
PROBE tests: command cd /home/vova/repo && npm run check && npm test
PROBE deploy_live: http_ok https://host/health contains 3f2a9c1
PROBE error_gone: command ! journalctl -u app --since '2026-09-27 18:00' | grep -q 'TypeError: x'
PROBE staging: skip у репо нет staging
```

Проверка `probes_declared` не пропустит шаг, если какая-то проба не объявлена. Последнее объявление побеждает, так что шаг может уточнить пробу позже.

**Нужен человек.** Шаг пишет вопрос в журнал и отвечает `DURABLE: failed: BLOCKED-ON-USER: <вопрос>`. Ретраев нет, владельцу сразу приходит вопрос. После ответа чат-агент дописывает ответ в журнал и вызывает `task_item_resume`: шаг продолжится хоть через неделю, план не забывается. Если за это время план стал неактуальным, шаг это увидит по журналу и скажет.

## 6. Как запускать

1. В чате: юзер просит фичу, баг или новый сервис. Агенту подсказывается нужный плейбук (авто-предложение выбирает `debugging` / `new-software` / `feature`).
2. **Intake — в чате, до активации.** Durable-шаги работают без чата, поэтому диалог о ценности, шагах и доступах ведёт чат-агент.
3. `playbook_run(playbook_id, goal)` → черновик плана и `run_notebook`. Чат-агент пишет в журнал раздел `## Intake`.
4. Юзер говорит «запускай» → `task_update status=active`. Дальше план идёт сам: шаги, ожидания, уведомления о вопросах и итоге.

---

## 7. Ограничения v1 и что дальше

- Ответ на BLOCKED-ON-USER дописывает в журнал чат-агент по инструкции из уведомления. Детерминированного роутинга «reply → план» пока нет.
- `ci_green` не отличает «ещё идёт» от «упал»: ожидание ждёт до таймаута (autofix может успеть починить).
- Упавший гейт `verify-local` останавливает план, а не возвращает к `implement`. После фикса — `task_item_resume`.
- Тик исполнителя — 5 минут, поэтому `poll_sec` меньше 300 фактически не работает.
