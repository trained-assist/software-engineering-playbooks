## 1. Три плейбука

| Плейбук | Когда | Ядро |
|---|---|---|
| `feature` | Самый частый: фича/изменение в существующем продукте | сценарий → исследование → флаги сложности → proposal → issue → **песочница** → реализация → PR → CI → merge → деплой → проверка в реальности → наблюдение → архивация |
| `debugging` | Баг, регрессия, ошибка в логах | контекст → **воспроизведение (лестница R)** → корневая причина → план фикса → issue → фикс с регрессионным тестом → PR → CI → merge → деплой → **ждём, не вернётся ли ошибка** → разбор |
| `new-software` | Новый модуль/сервис с нуля, свобода архитектуры (Playbook Zero) | сценарии → **разведка инфраструктуры и доступов** → аналоги (build vs buy) → флаги → варианты, ранжированные по песочнице (ADR) → эпик → песочница → каркас репо → ходячий скелет → PR/CI/merge → go-live → проверка → следующие сценарии как `feature` |

## 2. Подход: Sandbox-Driven Development (SbDD)

Сейчас все говорят про *specification-driven development* (OpenSpec, GitHub
Spec Kit, Kiro). По сути это старая хорошая практика «сначала договорись, что
строим» (user stories, BDD, RFC) в новой обёртке для LLM. Она нужна — но она не
главный рычаг скорости агента.

**Тезис.** Агент бесконечно быстрее человека в цикле «изменил → увидел
результат → поправил», *если цикл замкнут без человека*. Поэтому скорость
агентной разработки определяется не качеством спеки, а тем, насколько полную и
свободную песочницу агент получил:

```
скорость агента ≈ 1 / (время замкнутого цикла без участия человека)
```

**Формулировка:** *Sandbox-Driven Development — сначала исполняемая петля,
которая воспроизводит сценарий пользователя, потом код, который её проходит.*
(Альтернативное имя из черновика — execution-loop driven.) Порядок артефактов:

1. **Сценарий** (ценность + шаги) — *что* должно работать и для кого.
2. **Песочница** — одна команда, которая прогоняет эти шаги и **сейчас падает по
   правильной причине**. Уровень автономности S0–S5 и время цикла названы явно.
3. **Proposal / дизайн** — наименьшее изменение.
4. **Код** — срезами, прогоняя песочницу после каждого.

Спека говорит *что*, песочница *доказывает*. Спека без петли = агент пишет
вслепую (S0–S1) и ждёт человека на каждой проверке.

Отношение к известным практикам: это TDD, поднятый с уровня функции на уровень
сценария **и окружения**; BDD, где шаги сценария исполняемы; «walking skeleton»
(Cockburn / GOOS) как первый результат нового проекта; hermetic/ephemeral
environments из DevEx. Метрики DORA (lead time, частота деплоя, change-fail
rate, MTTR) — внешнее следствие короткой петли.

**Лестница S** (в `library/step-types.json`, рендерится в шаги):
S5 полный автономный e2e-цикл → S4 стейджинг, куда агент сам деплоит и где сам
смотрит → S3 автотесты с моками → S2 частичный запуск, внешнее проверяет человек
→ S1 только статика → S0 вслепую. S4–S5 = «проект выглядит несложно, пилим».

## 3. Сверка с индустрией

| Практика | Что берём | Где у нас | Что не берём и почему |
|---|---|---|---|
| **OpenSpec** (explore → propose → apply → archive) | Разделение «исследовать / предложить / применить / архивировать»; **spec delta** (ADDED/MODIFIED/REMOVED) и её слияние в живые спеки при архивации | типы `explore-context`, `propose-change`, `implement`, `archive` | Не ставим как инструмент: файловая структура `openspec/` абстрактна и ничего не исполняет. У нас этапы — durable-план с проверками, моделями по шагам и ожиданиями |
| **GitHub Spec Kit** (constitution → specify → clarify → plan → tasks → implement) | `clarify`: ≤5 точечных вопросов, у каждого рекомендуемый ответ; constitution = README/CLAUDE.md правила репо | `define-use-case` (п.6), `repo-bootstrap` | Отдельный артефакт на каждую фазу — избыточно для агента; держим в issue + сценарии |
| **Kiro / EARS** (Mavin, 2009) | Ожидаемый результат шага как «КОГДА <событие> ТОГДА система <ответ>» — однозначно проверяемо, дешёвая модель пишет по нему тесты | `define-use-case` (п.4) | Полный EARS-словарь (WHILE/WHERE/IF) — по необходимости |
| **User story / INVEST / BDD** | Ценность как результат для актора; шаги с конкретными функциональными блоками → тесты | `define-use-case` | «As a … I want …» шаблон — заменён ценностью-результатом (может быть негативной) |
| **Confidence Meter** (Itamar Gilad) | Лестница доказанности ценности V0–V5; низкий уровень не блокирует, а явно объявляется риском | ладдер `value-evidence` | Числовой скоринг ICE/RICE — не нужен |
| **Shape Up** (appetite, rabbit holes, no-gos) | Челлендж требований, которые раздувают систему; не-цели | `requirements-complexity`, флаги ⚪🟢🟡🔴⚫ | Циклы по 6 недель — не про агентов |
| **ADR** (Nygard) | Решение по архитектуре с отвергнутыми вариантами | `solution-options` | — |
| **Walking skeleton** (Cockburn), GOOS | Новый софт = один сценарий насквозь + CI + деплой первым | `new-software`: `sandbox` → `repo-bootstrap` → «Ходячий скелет» | — |
| **Научная отладка / TRAFFIC** (Zeller: Track, Reproduce, Automate, Find origins, Focus, Isolate, Correct), git bisect, 5 почему | Воспроизведение до фикса, гипотезы проверяются наблюдением, регрессионный тест из воспроизведения | `bug-context`, `reproduce`, `root-cause`, лестница R0–R5 | — |
| **Blameless postmortem** (Google SRE) | Хронология, причина, почему не поймали, что добавили | `archive` в `debugging` | Полный формат — только для значимых багов |
| **Temporal / AWS Step Functions** (durable timers, `await condition`, signals, wait state, callback token) | Шаг плана спит до условия/сигнала/таймера и переживает рестарты | движок: `wait` шага, `task_item_wait` / `task_item_wake` | Отдельный оркестратор не нужен: 5-минутный тик + SQLite |
| **Immutable PR** (правило репо) | PR — одноразовая попытка; фикс CI — новая ветка/PR | `open-pr`, `ci-green` | — |

**Про `/opsx:archive`** (в черновике — «не до конца понимаю»). В OpenSpec
архивация = слить дельту спеки изменения в «живые» спеки (`openspec/specs/`) и
убрать изменение в архив — чтобы источник истины всегда описывал систему *как
она есть*, а не историю правок. У нас ровно это и делает шаг `archive`: слить
изменения сценария в `docs/user-scenarios/`, обновить `requirements-log.md`,
закрыть/обновить issue, сохранить сжатую выжимку решений и граблей (дешёвой
моделью) — плюс для багов QA-лог.

## 4. Насколько детализировать: три уровня

1. **Плейбук** (шаблон): стадии → **типизированные шаги** (13–16 штук).
2. **Библиотека типов шагов** (`library/step-types.json`, 24 типа): у каждого —
   контракт (роль, уровень модели, бюджет контекста, проверка, таймаут),
   **типичные под-шаги**, Definition of Done, привязанные лестницы/флаги,
   соответствие OpenSpec. Один тип используется в нескольких плейбуках
   (`define-use-case`, `implement`, `ci-green`, `archive`…), правится в одном месте.
3. **Экземпляр** (durable-план конкретной задачи): `playbook_run` компилирует
   плейбук под цель; под-шаги рендерятся в инструкцию шага **чек-листом**, и
   агент проходит его целиком за один ран («чик-чик-чик»), отмечая каждый пункт
   ✅ / ⏭ с причиной.

**Правило «шаг или под-шаг».** Новый *шаг* заводится только на границе, где:
(а) меняется исполнитель/уровень модели, (б) нужна проверка-checkpoint с
доказательствами, или (в) процесс должен ждать внешнего события. Всё остальное —
под-шаги внутри одного рана. Больше шагов = больше ранов, больше холодных
стартов без памяти; больше под-шагов = подробнее чек-лист в одном ране.

**Непрерывность.** Каждый шаг — новый ран без памяти. Поэтому (движок) шаг
получает `[ИТОГИ ПРЕДЫДУЩИХ ШАГОВ ПЛАНА]` — выжимку блоков «ИТОГ ШАГА», которыми
агент обязан заканчивать каждый шаг, а «бумаги учёного» лежат в GitHub issue
(`plan-declaration`), куда шаги дописывают прогресс.

## 5. Время: процесс живёт, спит и просыпается

Главная боль черновика: агент не должен ждать сообщений «деплой закончился»,
«креды прислал» — и не должен забыть план, если ответ придёт через 3 дня.
Решено в движке (`trained-assist-agent`, `docs/specs/durable-wait-until.md`):

| Ситуация | Как выражено в плейбуке |
|---|---|
| Ждём CI | `ci-green`: `task_item_wait(until: {ci_green: <PR>})`; красный CI будит сразу («окончательно не выполнилось»), агент чинит |
| Ждём мерж | `merged`: programmatic-шаг с `wait` (опрос 5 мин, до 24 ч) — без модели вообще |
| Ждём деплой | `deployed`: `until: {http_ok: {url: /health, contains: <sha>}}` или статус workflow run |
| Ждём креды от пользователя | `until: {credential_present: "<service>"}`, таймаут до 7 дней — через 3 дня план продолжится сам |
| Ждём ответ пользователя | `awaiting_user: true`; в каждом чат-ране профиля видно «план ждёт ответа», ответ будит план через `task_item_wake` |
| Ждём повтор ошибки в логах | `reproduce` / `confirm-fixed`: `until: {command_exit_zero: "journalctl … \| grep -q '<ошибка>'"}` — процесс спит и просыпается, когда ошибка появилась |
| Наблюдаем сутки | `observe`: `sleep_sec: 86400` |
| Ждём другой план | `until: {task_done: "<plan id>"}` |

Свойства: опрос детерминированный (без LLM), не тратит попытки шага, переживает
рестарт сервера, ждущий шаг блокирует следующие. На пробуждении агент получает
блок «ПРОБУЖДЕНИЕ»: что ждали, что произошло (условие / ответ / таймаут) — и
**сам решает**, актуален ли ещё план (продолжить, подождать ещё, напомнить,
признать план неактуальным). Уведомления владельцу — хуки плейбука
(`task_done` / `task_failed` / ключевые `on_complete`); детальная политика «в
какой чат» — отдельный вопрос, не блокирует.

## 6. Лестницы и флаги (коротко; полные тексты — `docs/playbooks/step-library.md`)

- **V0–V5 — доказанность ценности.** Нетривиальная фича при V ≤ 1 → явно
  объявить риск пользователю и предложить, что добавить.
- **R0–R5 — воспроизведение бага.** Цель — поднять до R5 (автотест) до фикса;
  фикс при R < 3 — «спекулятивный» и обязательно подтверждается наблюдением.
- **S0–S5 — автономность песочницы.** Всегда целиться в максимальный S.
- **Флаги требований ⚪🟢🟡🔴⚫.** ⚪ прозрачный (не меняет модель) → 🟢 локальный
  аддитивный → 🟡 общие контракты/данные/вторая платформа → 🔴 модель доступа и
  прав, безопасность, биллинг, необратимые миграции → ⚫ неоднозначность
  (пересекающиеся сценарии с разным поведением). 🔴 и ⚫ челленджим всегда: цена в
  состояниях × сценариях тестирования и дешёвая альтернатива. Требование живёт,
  только если идёт из задачи или из реального ограничения *другой* части системы —
  «так уже написано» не источник требований.

## 7. Как пользоваться

```text
playbook_run(playbook_id: "feature", goal: "Экспорт отчёта в CSV", vars: {repo: "trained-assist/trained-assist-agent"})
  → черновик плана (15 шагов, видно в task_get / checklist.md проекта)
task_update(task_id, status: "active")
  → тик каждые 5 мин исполняет шаги разными моделями, спит на ожиданиях,
    уведомляет владельца о ключевых событиях и о застревании
```

На старте dev-задачи в боте агент сам предлагает подходящий плейбук (feature /
debugging / new-software), но **никогда не активирует** план без решения
пользователя.

Правка процесса: меняешь `library/step-types.json` (общее) или
`playbooks-src/<id>.json` (специфика) → `npm run build:playbooks` → PR. Уже
запущенные планы не меняются (план пинит `playbook_id@version`; меняя смысл
шагов, поднимай `version`).
