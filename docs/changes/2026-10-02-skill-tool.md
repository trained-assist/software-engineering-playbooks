# 2026-10-02 — плейбук `skill-tool` (issue #53, план aa96d610)

Выжимка решений и граблей при создании и приёмке плейбука «Новый MCP-инструмент в доменном скиле».

## Решения

- **Пробный прогон — обязательная часть приёмки, не формальность.** Полный прогон
  `skill-tool@2` на реальном туле (`freelance_search` в `trained-assist-freelance-skill`,
  план 302d321a) поймал реальный баг: параметр `limit` был в описании модели, но отсутствовал в
  JSON-схеме — фикс в коде скила (PR #36) + ужесточённый тест. Без прогона баг уехал бы в прод
  как «тул есть, но половина аргументов не проходит».
- **Библиотечное репо деплоя не имеет.** Плейбуки живут в sibling-чекауте
  (`PlaybookStore.resolve`: profile → sibling → system), поэтому «задеплоено» =
  `git merge-base --is-ancestor <мерж> HEAD` в чекауте, а не зелёный deploy-джоб.
- **Выбор цели для прогона:** второй скил со staging-гейтом в CI, без hh-манифестов, read-only
  тул со свободным номером — `freelance_search`. hh-skill из-за манифестов брать тяжелее.
- **Сценарий — живой документ:** при архивации обновить под текущее состояние (номера тулов,
  закрытые открытые вопросы, выполненную приёмку), а не оставлять историю решений.

## Грабли

- **Архивация через N дней после мержа: ветка плана содержит squash-мерж.** PR смержен как
  squash (`447a692`), и ветка `eng/...-plan-aa96d610` после этого выглядит «не в main»
  (`merge-base --is-ancestor` → false), а `origin/main` уехал на 3+ PR (ci-setup/ci-run,
  epic-delivery, map-first #49). Лечится `git merge origin/main`: конфликты add/add в наших же
  файлах (skill-tool.json, README, tests) — **решать в пользу main** (наш контент уже в squash,
  main его же перегенерил); после этого ветка == main, и любая новая дельта — чистый diff.
- **PR неизменяем, а ветка — нет:** старые PR (#55/#56) закрыты/смержены, поэтому новые коммиты
  в эту же ветку идут новым PR — это легально и не нарушает правило «не пушить в открытый PR».
- **`docs/changes/` в рабочем дереве ветки может отсутствовать, хотя есть на `origin/main`** —
  не играть в слепого по `ls`; сверяться с `git ls-tree origin/main`.
- Стендинговая проверка «staging зелёный» в этом репо неприменима (джобы `ci` только тесты) —
  в теле PR явно фиксировать, что staging-job отсутствует, а гейт staging остаётся в плейбуке
  для целевых репо (issue #9).

## Что улучшил бы в плейбуке (предложение владельцу)

- Шаг «описание ↔ схема» ( drift ловил только внешний гейт §9): добавить в шаг «заготовка»
  исполняемую проверку «каждый параметр из описания есть в `properties` и наоборот» — тогда drift
  ловится локально, до прогона на реальном туле.
