# Изменение: плейбуки `ci-setup` + `ci-run` — прогон тестов ветки в облаке

Дата: 2026-09-30 · issue #51 · план 3e40a139 · репозиторий `software-engineering-playbooks`
(ядро: `trained-assist-agent` PR-A #1852).

## Что сделано

- Плейбук `ci-setup` (разовый, на репозиторий): analyze → change → explain, идемпотентен
  («уже настроено» не открывает PR), правка идёт PR-ом в целевой репо.
- Плейбук `ci-run` (частый, на ветку): MCP-тул `ci_run_branch(repo, ref, suite?, run_id?)`
  (диспатч + свой ран / статус + упавшие джобы + хвост лога), ожидание через
  `task_item_wait(until: {ci_run_green: …})` и `DURABLE: waiting`.
- Типы шагов `ci-setup`, `ci-run` (24 → 25 типов), общий `verify-local` переписан:
  локально — только быстрые unit/lint, полный набор — в облаке.
- Шаблон `templates/ci.yml`: `workflow_dispatch` (input ref/suite), своя `concurrency`,
  без `continue-on-error` и без шагов мержа/деплоя.
- Валидатор `ci_run_green` в ядре (`createDefaultRegistry`): pass / fail-final (будит сразу) /
  inconclusive — никогда «зелёный» молча.
- Песочница `npm run test:sandbox:ci` (S5, ~0.3 с): фейковый GitHub API, 48 проверок по шагам.

## Что узнали (грабли)

- **Реальная проверка поймала то, что песочница пропустила (issue #64).** Фейковый API не
  воспроизводил два свойства настоящего GitHub: (1) у эндпоинта jobs нет параметра `status`,
  его надо фильтровать по `conclusion` самим — тул отдавал «9 упавших джоб» вместо одной;
  (2) run object не несёт тестируемый ref (`head_branch` = ветка, ОТКУДА диспатчили, а не ref
  под тестом), поэтому выбор «своего» рана — только по снимку id до диспатча, а не по окну
  «свежайший за 60 с» (иначе два диспатча с разницей 7–16 с получали один и тот же раниид).
  Вывод: песочница доказывает логику шагов, но контракт внешнего API проверяется только живым
  прогоном — S3/S4 перед «verify-real done».
- **«Мерж ≠ прод» для этого репо:** у него нет своего деплой-workflow, прод читает его как
  sibling-чекаут ядра (`deploy.sh:149`, `ensure_sibling`), а тот синкается только при деплое
  ядра с новым SHA. Поэтому после мержа PR #54 прод-чекаут `/home/vova/trained-assist-engineering`
  синхронизировали вручную (fetch + reset --hard origin/main).
- **Порядок мержей R2:** валидатор `ci_run_green` в ядре обязан доехать раньше плейбуков,
  иначе `task_item_wait` отвергает неизвестный ключ условия.
- **Стек — ветка плана:** при `git merge origin/main` в уже смерженную (squash) ветку
  конфликты разрешаются `-X theirs` по файлам, где side-main уже победил (skill-tool и пр.).
